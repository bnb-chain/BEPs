# BEP-714: Improve Network Availability with Earlier Validator Maintenance

## 1. Summary

Reduce the impact of unavailable validators by shortening backup waiting time and introducing automatic maintenance before economic penalties apply.

## 2. Motivation

Previous block-interval upgrades, including [BEP-520](./BEP-520.md), [BEP-524](./BEP-524.md), and [BEP-619](./BEP-619.md), scaled slashing thresholds to preserve approximately the same operator response time. However, scaling by block interval alone does not account for backup waiting time or consecutive block production.

For example, `3 * 50` approximately equals `0.45 * 333`, but the initial backup delay increased from 1 second to 2 seconds. With one unavailable validator and a healthy first backup, the sum of affected block intervals before the misdemeanor threshold increased from `(3 + 1) * 50 = 200 seconds` to `(0.45 + 2) * 333 = 815.85 seconds`. An eight-block affected turn takes approximately `(0.45 + 2) * 8 = 19.6 seconds`.

This proposal shortens affected turns and removes failed validators from the rotation earlier. It rebalances rather than preserves the recovery window: the time before losing accrued rewards grows somewhat, while the time before being jailed shortens. Section 4.2 quantifies both.

## 3. Specification

### 3.1 Parameter Changes

| Parameter | Current configuration | Proposed configuration | Mechanism |
| --- | --- | --- | --- |
| InitialBackOffTime | 2 seconds | 1 second | Hard fork |
| turnLength | 8 | 4 | Separate governance proposal |
| maintainSlashScale | 2 | 3 | Governance proposal |
| maintenanceThreshold | Not defined | 40 | New contract parameter |
| misdemeanorThreshold | 333 | 200 | Governance proposal |
| felonyThreshold | 1,000 | 600 | Governance proposal |

The block interval remains 0.45 seconds and the epoch length remains 1,000 blocks. The calculations below assume 21 mining validators.

### 3.2 Backup Waiting Time

Reduce `InitialBackOffTime` from 2,000 to 1,000 milliseconds in both block preparation and timestamp validation. Apply this change to both backoff paths: the normal backup sequence and the sequence used when the in-turn validator is excluded by the recent-signing rule. The latter retains zero delay for its first eligible backup. Backup ordering and spacing between subsequent ranks remain unchanged.

As in the existing implementation, select the backoff rule using the parent block's timestamp at the hard-fork boundary.

### 3.3 Earlier Automatic Maintenance

Extend [BEP-127](./BEP127.md) with a governable `maintenanceThreshold`, initially 40. Parameter updates must preserve:

```text
0 < maintenanceThreshold < misdemeanorThreshold < felonyThreshold
```

When the slash system transaction raises a validator's missed-block count to `maintenanceThreshold` or above without hitting a misdemeanor or felony boundary, SlashIndicator asks BSCValidatorSet to admit the validator to maintenance. Admission applies the existing BEP-127 eligibility rules and no penalty. If the validator is not eligible, nothing happens and the attempt repeats on each later missed block. This reuses the path through which a misdemeanor already admits a validator to maintenance; no new system transaction is introduced.

Existing maintenance capacity and once-per-day limits remain in effect. There is no waiting queue: when capacity is available, it goes to the first eligible validator whose slash transaction is processed, regardless of which validator reached the threshold first. Manual maintenance remains available.

Automatic admission consumes the validator's once-per-day maintenance allowance. A validator that is admitted, exits, and fails again on the same UTC day cannot re-enter through any path and remains under ordinary slashing until the next daily validator update. Automatic admission also requires maintenance to be enabled, that is, non-zero `maxNumOfMaintaining` and `maintainSlashScale`; as in BEP-127, a fresh deployment enables it through governance or through the first manual `enterMaintenance()` call, and setting `maxNumOfMaintaining` to zero disables automatic admission as well.

Admission is a state change in the block that contains the slash transaction. The next epoch header selects validators from the preceding block's contract state and excludes validators that are still in maintenance at that block; a validator that has already exited without felony, manually or through the daily forced exit, remains eligible for selection like any other working validator. For a validator still in maintenance, removal from the rotation takes effect at the next epoch boundary and then follows the existing snapshot transition rules, regardless of when within the epoch the threshold was reached. Ordinary missed-block counting stops at contract entry, even if snapshot adoption is still pending.

### 3.4 Maintenance Accounting

Include the missed-block count recorded before maintenance in the exit calculation:

```text
maintenanceCount = floor((exitHeight - entryHeight) / miningValidatorCount / maintainSlashScale)
totalCount       = entryMissedBlockCount + maintenanceCount
```

Apply this formula to both manual and automatic maintenance. On explicit exit or daily forced exit, apply felony when `totalCount >= felonyThreshold`. Otherwise apply misdemeanor when

```text
floor(totalCount / misdemeanorThreshold) > floor(entryMissedBlockCount / misdemeanorThreshold)
```

Between two resets of the count, ordinary slashing charges each multiple of `misdemeanorThreshold` as the count passes it, so at entry no uncharged multiple lies at or below the entry count. The comparison therefore charges at most once per settlement, even if several multiples were crossed during maintenance, and does not re-charge a multiple that ordinary slashing charged before entry. Daily decay and felony lower the count, after which the same numeric multiples can be charged again as new crossings.

A validator evicted by StakeHub while in maintenance, for example for a malicious vote or for self-delegation falling below the minimum, leaves maintenance through the existing felony path without settlement; its recorded missed-block count is left unchanged, as today.

After a non-felony exit, persist `totalCount` as the validator's missed-block count so that ordinary slashing continues from it. Felony resets the count as in ordinary felony processing. Daily decay follows forced-exit settlement. Ordinary slashing keeps its exact-multiple rules for both thresholds.

Changes to `misdemeanorThreshold` or `felonyThreshold` are not retroactive. Ordinary slashing charges the next multiple of the new threshold that the count reaches, and a settlement compares entry and total counts under the thresholds in force at exit. The validator count, scale, and thresholds are read at settlement, following the existing maintenance mechanism. Penalties are settled on exit; reaching an equivalent threshold during maintenance does not immediately execute a penalty.

Sessions already active at the upgrade have no recorded entry count and settle with the previous independent-count formula.

## 4. Rationale

### 4.1 Shorter Affected Turns

With the proposed parameters:

```text
Current:  (0.45 + 2) * 8 = 19.6 seconds
Proposed: (0.45 + 1) * 4 =  5.8 seconds
Reduction: approximately 70%
```

This estimate assumes one unavailable in-turn validator and timely production by the first eligible backup. It describes the affected turn, not a worst-case transaction inclusion guarantee. Builder-only failures may be handled by local block production; private transaction delays also depend on routing and fallback behavior.

[BEP-520](./BEP-520.md) increased backoff to reduce reorganizations caused by delayed propagation. Returning to 1 second therefore requires validating propagation and reorganization behavior under load. Reducing `turnLength` also makes producer handovers more frequent, so throughput should be evaluated alongside availability.

BEP-520 also raised `turnLength` to 8 to limit the effect of deliberately delayed blocks at validator-set transition points and to keep per-epoch opportunities similar across validators. Halving `turnLength` partially reverses the first mitigation and must be evaluated together with the shorter backoff under the same transition scenarios. Per-epoch opportunities become 44 or 48 because `1000 / (21 * 4)` is not an integer; this proposal accepts that 9% spread. Shorter turns reduce the number of blocks needed for natural finality when fast finality is unavailable.

### 4.2 Earlier Removal and Recovery Time

With admission on the 40th missed block, the entry count is 40 whenever admission succeeds immediately. If capacity or the daily allowance blocks admission, the count keeps growing and admission is retried on each later miss; the misdemeanor path at 200 remains as a fallback. The estimates below assume immediate admission.

Removal from the rotation happens at the next epoch header plus snapshot adoption, regardless of when the threshold was reached. With 21 validators and `turnLength = 4`, a validator has 44–48 opportunities per 1,000-block epoch, so up to about one epoch of its turns can still be affected after contract entry; those misses are not counted.

With `maintainSlashScale = 3`, the combined-count model gives:

| Interval | Calculation | Estimated duration |
| --- | --- | --- |
| Maintenance entry to misdemeanor threshold | `21 * 0.45 * (200 - 40) * 3` | 75.6 minutes |
| Maintenance entry to felony threshold | `21 * 0.45 * (600 - 40) * 3` | 4.41 hours |
| Between the two thresholds | `21 * 0.45 * (600 - 200) * 3` | 3.15 hours |

These estimates assume immediate admission and stable parameters. The actual entry count, validator count, and daily settlement can change the available recovery time.

Affected opportunities before contract entry total about `40 * 1.45 = 58 seconds` of block intervals, including `40 seconds` of additional backup waiting; up to one further epoch of turns can be affected before removal. Backup blocks can still include transactions, so this is not a period of complete network unavailability.

Elapsed time differs from these affected-interval sums because the other 20 validators keep producing between the failed validator's turns. Each missed block advances the chain by about `21 * 0.45 + 2 = 11.45 s` today and `21 * 0.45 + 1 = 10.45 s` under the proposal. Under the current configuration a failing validator reaches the misdemeanor threshold after about 63.5 minutes (`333 * 11.45 s`), enters maintenance through that misdemeanor, and reaches felony after a further 5.25 hours (`1000 * 21 * 2 * 0.45 s`). If maintenance is unavailable, ordinary slashing reaches felony after about 3.2 hours (`1000 * 11.45 s`). Under the proposal, the 40th miss occurs after about 7 minutes (`40 * 10.45 s`).

Maintenance penalties are settled on explicit or daily exit, so the maintenance rows below give the earliest exit at which the penalty applies, not an automatic execution time.

| Interval from failure | Current | Proposed |
| --- | --- | --- |
| Earliest misdemeanor (loss of accrued income), settled on exit | about 63.5 minutes | about 83 minutes |
| Earliest felony through maintenance, settled on exit | about 6.3 hours | about 4.5 hours |
| Felony without maintenance | about 3.2 hours | about 1.7 hours (`600 * 10.45 s`) |

The proposal lengthens the window before income loss somewhat and shortens the window before jailing by about 30%. This trade-off is intended: the misdemeanor now falls inside maintenance, after the network has already been protected, while the felony window stays at several hours.

## 5. Backward Compatibility

The backoff and contract changes activate together in Jenner; activation timestamps remain unscheduled. No new system transaction is introduced. The new cross-contract calls are used by the existing slash and maintenance paths, so on every supported network the new ValidatorSet and SlashIndicator bytecode MUST be installed in the same fork block. Neither partial state is supported: with only SlashIndicator upgraded, a slash that reaches `maintenanceThreshold` reverts and that miss is not counted; with only BSCValidatorSet upgraded, new maintenance sessions cannot exit, including the daily forced exit, and a misdemeanor entry snapshots the count before the old SlashIndicator stores its increment.

Preserve existing missed-block indicators and settle maintenance sessions already active at the fork with the previous independent-count formula. New sessions use the combined formula.

Governance changes affect parameters read at settlement. Lowering `felonyThreshold` also changes daily missed-block decay from `1,000 / 4 = 250` to `600 / 4 = 150`. Operators must account for these changes when planning maintenance.

## 6. Implementation Plan

1. Activate the backoff change, `maintenanceThreshold = 40`, threshold-triggered admission, and combined accounting through a hard fork.
2. Execute a governance proposal setting `maintainSlashScale = 3`, `misdemeanorThreshold = 200`, and `felonyThreshold = 600`.
3. Execute a separate governance proposal changing `turnLength` from 8 to 4, following its existing epoch/snapshot activation rules.

The final estimates apply once all changes are effective. Validate intermediate configurations, epoch and daily boundaries, maintenance admission limits, combined settlement, and behavior under network delays before activation.
