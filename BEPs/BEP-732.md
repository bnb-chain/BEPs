## 1. Summary

BSC supports three block-production paths: local mining by the validator, a Bid (`SendBid`) that the validator simulates and completes, and a BidBlock (`SendBidBlock`, [BEP-675](./BEP-675.md)) that the validator seals without simulation.

This BEP introduces Block Access Lists (BALs, [EIP-7928](https://eips.ethereum.org/EIPS/eip-7928)) across all three paths. A producer can prepare a candidate parent state from the parent's BAL and start constructing the next block while fully verifying the parent. For local mining, this removes a wait at validator handover, when the incoming validator must import the outgoing validator's block. During consecutive locally executed blocks, the validator already has the parent execution result and does not gain another saved parent-execution pass from this mechanism.

BALs also enable state prefetching and parallel verification of received blocks. The complete BAL is generated by the party that executes the final block, and the validator includes its commitment in the Parlia-signed header and propagates it with the block:

| Path | Complete BAL generated by |
| --- | --- |
| Local mining | The validator executing its locally selected transactions and finalizing the block |
| Bid | The validator simulating the bid, adding any further transactions and finalizing the block |
| BidBlock | The builder executing the complete submitted block, including unsigned system transactions |

## 2. Abstract

When a producer needs to import a received parent, the existing production paths are:

- **Local mining (validator handover):** Import parent block → Validator constructs block locally → Block produced
- **Bid:** Import parent block → Builder constructs bid → Validator simulates bid → Block produced
- **BidBlock:** Import parent block → Builder constructs BidBlock → Block produced

A BAL records every account and storage slot a block touches and its post-transaction state changes. Its final values can be applied to a verified base state to prepare a candidate parent state without waiting for parent execution. The resulting paths are:

- **Local mining (validator handover):** Prepare candidate parent state → Validator constructs block locally while verifying parent → Parent verification gate → Block produced
- **Bid:** Prepare candidate parent state → Builder constructs bid while verifying parent → Parent verification gate → Validator simulates bid and records BAL → Block produced
- **BidBlock:** Prepare candidate parent state → Builder constructs BidBlock while verifying parent → Parent verification gate → Block produced

The gate requires successful local parent verification before a builder submits a bid or BidBlock, and successful parent import before a validator seals a locally constructed block or accepts a builder submission. Verification failure or a reorganisation cancels the dependent construction. A matching local execution state may be reused instead of applying the BAL; consecutive local mining already has this state and does not need the handover import step.

Parallel transaction verification within the parent and overlapping parent verification with next-block construction are separate optimizations. The overlap does not require parallel parent execution: the parent can still be verified sequentially in the background. This BEP does not use the parent's BAL to parallelize the unknown transactions of the next block, and `SendBid` simulation remains sequential.

## 3. Motivation

Waiting for a received parent to finish executing reduces the time available to construct the next block. This affects builders on both MEV paths and local mining at validator handover: the incoming validator must obtain the outgoing validator's post-state before selecting and executing its own transactions. A parent BAL makes a candidate post-state available before full verification completes, allowing these tasks to overlap.

The paths also have different execution costs. BEP-675 removes pre-seal validator simulation for BidBlocks, but the producing validator still executes and verifies each sealed BidBlock after broadcast. This can delay acceptance of submissions for its next block and create a verification backlog at higher gas limits. `SendBid` retains validator simulation. In contrast, local mining and `SendBid` already execute the final block before sealing and reuse that execution result for insertion; they do not require a second full execution after broadcast.

Consecutive locally executed blocks therefore do not have the same parent-import bottleneck as a validator handover. Their producer already has the parent state, so this BEP does not count another eliminated parent-execution pass for them. A parent merely sealed from an external BidBlock is different: its BEP-675 asynchronous verification still has to complete, even if the validator remains the same.

Higher gas limits increase execution, verification and propagation costs. BAL prefetching and parallel verification can shorten received-block processing, while overlapping parent verification with construction enlarges the building window. BAL recording and transport also add costs, so the benefits must be evaluated for each production path. On the Bid path, the validator records the BAL during its existing sequential execution; this BEP does not accelerate bid simulation with a BAL.

## 4. Specification

This BEP activates with the BSC hard fork that adopts EIP-7928. From that fork, every block header carries `BlockAccessListHash = keccak256(rlp(BAL))`, and the BAL encoding, validation rules, size constraint and block access index assignment follow EIP-7928 as adopted by BSC, including the indices of Parlia system transactions.

### 4.1 Parent State and Verification

The following rules apply to early construction by both a local validator and an external builder. Let `N` be the received parent and `N+1` the block being constructed.

1. **Check the parent and BAL.** The state of `N-1` must be available and verified. Check the header and Parlia seal of `N` against its parent branch. Before using a received BAL, check its canonical encoding, ordering, indices and size, and require `keccak256(rlp(BAL))` to match `N.BlockAccessListHash`. Commitment verification alone does not establish execution correctness.
2. **Prepare an isolated candidate state.** Apply the final post-values of the BAL to the state of `N-1`, or reuse a local execution result that matches the final parent. The BidBlock-specific matching rules are in [Section 4.3](#43-builder). Do not commit this candidate state, publish it as the canonical head or advance the canonical transaction pool. Select transactions against the candidate state and exclude transactions already included in `N`.
3. **Use the candidate parent context.** Construct `N+1` using the received header and branch of `N`, including the required ancestor headers and Parlia context. Header-dependent execution, including `BLOCKHASH(N)`, must resolve against that branch even though `N` is not yet imported; reading only the old canonical head is insufficient.
4. **Verify the parent while constructing the child.** If `N` is not yet fully verified, execute and validate it independently, using BAL-driven prefetching of accounts, code and storage. Its transactions may be verified in parallel, but sequential parent verification is also compatible with early construction. Check the rebuilt BAL, state root, receipts and other existing block-validity conditions. Any state derived from the BAL must agree with the verified result.
5. **Enforce the verification gate.** A builder must not submit a bid or BidBlock until its local verification of `N` succeeds. A validator must not seal a locally constructed child until `N` has been successfully imported and remains the eligible parent, and continues to accept builder submissions only for imported parents. Failed verification, a derived-state-root mismatch or a reorganisation cancels all dependent work and discards its candidate state.

If a BAL is missing or fails the attachment checks, fetch it or execute the parent normally and rebuild the BAL to check the header commitment. Without a usable BAL or a matching local execution state, construction waits for parent execution. Missing data alone does not make a block invalid or trigger BEP-675 revocation. An execution-confirmed mismatch with the committed BAL makes the block invalid.

### 4.2 Local Mining

**Validator handover.** When the parent was produced by another validator and its import is still pending, the incoming validator may use [Section 4.1](#41-parent-state-and-verification) to start constructing its first local block before parent import completes. The parent verification task and the local miner use separate mutable state. Mining triggers and transaction selection must support this candidate parent without advancing the canonical head, and the resulting candidate cannot be sealed until the parent verification gate passes.

**Consecutive local blocks.** When the validator continues producing blocks whose parent it executed locally, it reuses the parent execution result through the existing insertion path. It does not apply the parent BAL or replay the parent merely to start the next block. The parent-import overlap described above concerns validator handover, not this consecutive local-mining case. A preceding externally built BidBlock remains subject to the BEP-675 verification rules.

**Record, finalize and seal.** The validator generates a complete BAL during the normal execution of its local candidate:

- record block-begin protocol operations, the selected user transactions, Parlia system transactions and remaining protocol state changes under the BSC adoption of EIP-7928;
- assign transaction indices from their actual positions in the final block; keep the BAL and execution state consistent when reverting failed inclusion attempts, dropping transactions or replacing a candidate;
- complete BAL recording during finalization, set `BlockAccessListHash = keccak256(rlp(BAL))` in the final header, and cover it with the Parlia seal;
- reuse the executed state and receipts for normal block insertion, then propagate the complete BAL with the sealed block through the broadcast rules in [Section 4.5](#45-validator). No BidBlock submission or additional full execution is required.

**Prefetching during mining.** Existing `PrefetchMining` remains a cache-warming optimization. Access locations from an earlier candidate or parent BAL may be used as bounded prefetch hints, but they do not determine the next block's accesses or final BAL. Prefetch trial execution skips nonce checks and discards its state changes; its results must not be substituted for formal execution or the BAL recorded from the selected candidate. This optional cache optimization is separate from the parent-import overlap at validator handover.

### 4.3 Builder

The builder constructs and submits a BidBlock as specified in BEP-675, with the following changes:

1. **Record the BAL** — while executing user transactions and the unsigned system transactions, record the BAL as EIP-7928 specifies. Transactions and bundles that the builder tries and then drops are removed together with their BAL entries. Signing does not affect EVM state changes, and the BAL contains no transaction hashes, so the BAL recorded with unsigned system transactions remains valid after the validator signs them.
2. **Commit the BAL** — set `BlockAccessListHash` in the header to `keccak256(rlp(BAL))`.
3. **Submit the BAL** — attach the BAL to `BidBlockArgs`, or to the gRPC request ([Section 4.6](#46-grpc-transport)).

**`BidBlockArgs` data structure:**

```go
type BidBlockArgs struct {
    BidBlock        *BidBlock
    BlockAccessList hexutil.Bytes // EIP-7928 RLP-encoded BAL
    Signature       hexutil.Bytes
}
```

- **`Signature`** — unchanged: the builder signs `keccak256(rlp(header))` of the header it submits. The header carries `BlockAccessListHash`, so the BAL is bound to the BidBlock without a separate signature.
- **`BlockAccessList`** — required for every BidBlock from the activation fork.

**Building on an unimported parent.** The builder follows [Section 4.1](#41-parent-state-and-verification). If `N` is its own BidBlock, it may reuse the post-state of its own execution after confirming that `N` matches it by `ParentHash`, `StateRoot` and the execution results; `TxHash` and the block hash are not used for matching, because the validator signs system transactions and rewrites `Extra`. This reuse does not waive validation of the final sealed parent or the submission gate. Otherwise, the builder derives the candidate parent state from the final block's BAL.

**SendBid.** The builder submits candidate transactions and a bid as today, without a BAL. The existing `RawBid`, `BidArgs` and bid signature are unchanged. The validator records and produces the complete BAL while simulating and finalizing the selected bid ([Section 4.5](#45-validator)).

Because the validator adds transactions, a builder cannot reuse its own execution state for a block built from its bid, and builds on such a block through the final block's BAL. It can still use the parent block's BAL to start building its bid before parent import completes, subject to the verification and submission rules above.

### 4.4 MEV-Sentry

MEV-Sentry forwards the BAL with the BidBlock without additional processing. On the gRPC path it forwards the BAL as raw bytes, like the BidBlock RLP, without re-encoding. On the `SendBid` path it forwards the bid and attaches `PayBidTx` as today; no BAL is transmitted on this path.

### 4.5 Validator

The validator processes BidBlocks and bids in the following stages and selects the best one as specified in BEP-675. Where the two MEV paths differ, each stage describes both. Local mining follows [Section 4.2](#42-local-mining) and shares the Parlia commitment and broadcast rules below; the asynchronous import stage applies specifically to BidBlocks.

**1. Pre-seal verification**

*BidBlock.* In addition to the BEP-675 header verification, the validator verifies, without EVM execution:

- the BAL is present and its size is within the EIP-7928 size constraint;
- `keccak256(BlockAccessList)` equals `BlockAccessListHash` in the header;
- the BAL is canonically encoded and satisfies the EIP-7928 ordering and index rules.

These checks establish that the BAL is the one committed by the builder-signed header and is within resource bounds; they do not establish that it is correct. Any failure causes immediate rejection. Once a BidBlock passes, the validator may start a bounded prefetch of the state the BAL declares.

*SendBid.* The validator simulates the bid as today, recording the BAL throughout the existing sequential execution:

- record block-begin protocol operations at block access index 0, then the bid transactions, any transactions merged from the validator's mempool, and `PayBidTx` in execution order;
- assign each transaction the block access index of its position in the final transaction list;
- retain the recorded BAL with the candidate execution state selected for sealing, and continue recording during finalization as described below.

No builder-supplied BAL or prefix comparison is required. Recording the BAL adds no extra execution pass.

**2. Finalize, assemble and seal**

As on each path today, with one change to the seal: from the activation fork, the header fields signed by the Parlia seal include `BlockAccessListHash`. The sealed BAL therefore cannot be replaced without invalidating the seal.

- *BidBlock* — the BAL is used as submitted: signing the system transactions does not change any state access, so the BAL and `BlockAccessListHash` stay unchanged.
- *SendBid* — the validator reuses the selected simulation state and continues recording while executing the system transactions and any remaining protocol state changes during finalization, using the indices defined by the BSC adoption of EIP-7928. It then sets `BlockAccessListHash = keccak256(rlp(BAL))` of the complete BAL in the header it assembles. The existing execution result is reused for block insertion; generating the BAL does not require replaying the block.

**3. Broadcast**

The BAL is pushed with the block, and fetched on demand only when it is missing:

- **Validator to EVN and proxied peers** — the validator sends the BAL together with the sealed block. Validators and builders receive new blocks through the direct broadcast of the Enhanced Validator Network ([BEP-563](./BEP-563.md)), so they get the BAL at the same time as the block.
- **Relaying nodes** — a node that receives a block with its BAL keeps the BAL and forwards it with the block, including when serving the block to peers that fetch it.
- **Missing BAL** — a node that receives a block without a BAL, or needs the BAL of an earlier block for synchronisation, fetches it over eth/71 ([EIP-8159](https://eips.ethereum.org/EIPS/eip-8159)).

The BAL is an optional field of `NewBlockPacket` and of each block in a `BlocksByRange` response, omitted when no BAL is attached. Support for this field is negotiated when peers connect, separately from eth/71, and the BAL is sent only to peers that support it.

**4. Asynchronous import**

After broadcasting a BidBlock, the validator imports the block as in BEP-675, using the BAL to prefetch the state it declares, continuing any prefetch started before sealing, and to execute the block in parallel:

- execute the block and rebuild the BAL from the actual execution;
- verify the rebuilt BAL against `BlockAccessListHash`;
- verify the state root, receipts root, logs bloom and gas used.

Any mismatch fails the import and triggers the BEP-675 permission revocation.

### 4.6 gRPC Transport

gRPC carries only `SendBidBlock`; `SendBid` and the other MEV APIs remain on JSON-RPC with their existing request formats. Only `BidBlockRequest` therefore changes: the BAL is a separate `bytes` field, carrying its EIP-7928 RLP encoding unchanged:

```proto
message BidBlockRequest {
  bytes bid_block_rlp = 1;
  bytes signature = 2;
  string validator_host_name = 3;
  // EIP-7928 RLP-encoded BAL, bound by BlockAccessListHash in the header.
  bytes block_access_list = 4;
  reserved 5 to 10;
}
```

- **Not inside `bid_block_rlp`** — MEV-Sentry decodes `bid_block_rlp` to verify the builder signature; a separate field lets it forward the BAL without decoding it.
- **Not a structured protobuf message** — the commitment is the `keccak256` of the RLP encoding, so the validator hashes the received bytes directly, before decoding them.
- **Message size** — the gRPC message limit of MEV-Sentry and the validator, currently twice the maximum block size, accounts for the BAL in addition to the BidBlock.

## 5. Backward Compatibility

This BEP requires a hard fork: it activates with the BSC adoption of EIP-7928 and changes the header encoding signed by the Parlia seal from that fork. Blocks before the fork are unaffected.

Local mining remains available alongside the `SendBid` and `SendBidBlock` paths, which continue to coexist as specified in BEP-675. All three produce a complete BAL from activation. The `SendBid` request and signature are unchanged. The `BidBlockArgs` field, the gRPC field and the block message fields are additive, and nodes negotiate support for the block message field during the bsc protocol handshake.

## 6. Security

Each node accepts a block only if its own execution rebuilds the BAL committed in the header and passes the existing checks; with a missing or unusable BAL, the node executes the block sequentially.

- **Replacing the BAL** — on the BidBlock path, the submitted BAL is bound by the builder-signed header. On local mining and Bid paths, the validator generates the BAL locally. After sealing, the BAL on all three paths is bound by the Parlia seal. A replaced BAL fails the hash check and is discarded before execution.
- **Incorrect BAL** — a BAL that matches the header but not the execution makes the block invalid on every path. For a BidBlock, the producing validator detects it during asynchronous import and revokes the builder as in BEP-675. The worst case remains one bad BidBlock per builder per revoke window; builder permission revocation does not apply to local mining.
- **Withholding** — a BidBlock without a BAL is rejected before sealing.
- **Building on an invalid parent** — a builder submits a bid or BidBlock only after verifying its parent, and a validator accepts submissions and seals locally constructed children only after the parent is imported and remains eligible. Candidate state is isolated, and dependent work is cancelled on failed validation or reorganisation.
- **Resource use** — the BAL is size-bounded by EIP-7928 and checked with one hash before use, and pre-seal prefetching is bounded and does not delay sealing.
- **Early exposure** — the BAL leaves the validator only after sealing, together with the block that reveals the same state changes.

## 7. Performance Analysis

The benefits differ across the three production paths:

| Path | Parent-verification overlap | Remaining production work |
| --- | --- | --- |
| Local mining | At validator handover, importing the outgoing validator's block overlaps local construction | Execute the locally selected transactions and finalize the block; consecutive locally executed parents already have reusable state |
| Bid | Builder construction overlaps verification of a received parent | Validator simulation remains sequential and produces the complete BAL |
| BidBlock | Builder construction overlaps verification of a received parent | Validator seals without simulation, then verifies the BidBlock asynchronously |

All three generate BALs that receiving nodes can use for prefetching and parallel verification. These benefits do not imply that transactions in a newly selected candidate can be executed in parallel using only its parent's BAL.

**BidBlock.**

For the BidBlock path, using the model of BEP-675, let `G` denote the gas limit in Mgas and `R` the EVM throughput; one pass over `G` takes `G/R` time. Let `s` denote the speedup of parallel execution against a BAL, and `t_apply` the time to check the BAL and derive the parent post-state from it.

- **BEP-675** — 2 EVM passes on the critical path (parent import + builder execution):
  `2·(G/R) + overhead = block_interval`
- **This BEP** — the builder starts after `t_apply`, and parent verification `G/(s·R)` runs in parallel with building:
  `max(t_apply + G/R, G/(s·R)) + overhead = block_interval`

When parallel verification finishes within the building time, the critical path contains a single EVM pass, and solving for `G` yields up to roughly twice the BEP-675 gas-limit ceiling, reduced by `t_apply` and by contention between verification and building. Equivalently, the interval during which builders execute and pack transactions is no longer shared with parent import. The BAL also shortens the asynchronous verification of sealed BidBlocks by the factor `s`, and adds to the BidBlock payload, which favors the binary gRPC transport.

On the SendBid path, validator simulation remains sequential and adds its own latency to the critical path, so the single-pass ceiling above does not apply. This path still benefits from overlapping parent verification with builder construction, and its final BAL enables parallel verification by receiving nodes and early construction of the next block. BAL recording and encoding have overhead, but require no extra EVM pass.

**Local mining at validator handover.** Let `T_import` be the time to import the received parent without BAL acceleration, `T_verify` the time to verify and import it with BAL support, and `T_build` the time to execute and finalize the next local candidate. For the same candidate workload, the relevant completion times are:

- **Before:** `T_import + T_build + overhead`
- **With BAL:** `max(T_verify, t_apply + T_build) + overhead_BAL`

The second expression includes the parent verification gate: local sealing waits for both parent import and candidate construction. `overhead_BAL` includes the remaining BAL recording, encoding and propagation costs. If a fixed production deadline is used instead, starting after `t_apply` rather than `T_import` provides additional packing time when `t_apply < T_import`. Actual gains depend on parent verification finishing in time and on CPU, memory and storage contention between the two tasks.

This handover model concerns the first locally constructed block after a validator change, when parent import is still pending. It does not apply to subsequent consecutive locally executed blocks: there is no separate full parent-execution pass to remove, and the producer reuses its parent state. The new BAL still helps receiving nodes, including the next validator at handover. Any benefit from mining-time prefetch hints must be measured separately; the BidBlock gas-limit estimate above must not be applied to every block in a consecutive local-mining run.

Overlapping parent verification with construction and accelerating parent verification internally are independent improvements. The overlap can be measured with sequential parent verification first; enabling BAL parallel verification can then reduce `T_verify`, but the two gains are not additive once construction becomes the limiting task.
