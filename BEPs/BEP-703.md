## 1. Summary

This BEP reserves a small fraction of the gas in every block — the **Payment Lane** — that only payment transactions may consume. The reservation is a per-block gas accounting rule, not a region of the block: payment and non-payment transactions remain freely interleaved, ordered, and priced exactly as today. The lane guarantees gas to payment transactions as a class; it does not promise that any one of them is included. And it only takes effect when the block would otherwise be full: in a block with space left over, nothing changes.

## 2. Motivation

BSC fixes the base fee at zero ([BEP-226](./BEP226.md)), so inclusion is decided entirely by priority-fee bidding. That works well in the common case, but every class of traffic bids for the same block space: when demand in one class pulses, it raises the price of inclusion for all the others. Payment transactions — stablecoin transfers, exchange deposits and withdrawals, remittances, merchant settlement — are hit hardest. They are time-sensitive, they appear in nearly every block, and they are the least able to defend themselves in a bidding contest, because the sender is an end user or a payment backend rather than an agent that re-prices block by block. So payments are the first traffic crowded out, and moving funds — the chain's most basic function — becomes unreliable precisely when the chain is busiest.

This is not a capacity problem: block space comfortably exceeds payment demand at all times, and BSC's throughput keeps rising. The defect is structural — block space is undivided, so congestion in one class spreads to unrelated classes. A bounded, protocol-level reservation for the payment class cuts that link, and it is cheap: payment transactions are individually small in gas, so the reservation is a small slice of the block, and the fee market and the ordering rules stay untouched.

## 3. Specification

### 3.1 Block Space Model

This section states the model in pictures; the rules that follow are its formalization. Every transaction is either a **payment transaction** or a **general transaction** — how that is decided is specified in [§3.2](#32-transaction-classification).

```
Legend   #  general tx gas    =  payment tx gas
         :  reserved for payment but unused - general may NOT take it
         .  block space nobody used - either class may take it

Schematic, not to scale: the payment lane is 5% of the block at the ratio of 3.6.1.


Today, with no reservation

                             <---------------- GasLimit ---------------->
  quiet                     [######====..................................]
  congested                 [############################################]
                             general demand alone fills the block; payment
                             traffic arriving during the pulse is not included


With the payment lane

                             <-------- general space ---------> <payment space>
  quiet                     [######............................|====:::::]
                             the block is not full; the lane changes nothing

  congested,                [##################################|===::::::]
  payment < paymentLaneQuota general stops at the lane boundary; the unused
                             part of the lane stays idle, and is not returned
                             to general

  congested,                [############################======|=========]
  payment > paymentLaneQuota payment filled the lane and overflowed past it;
                             the overflow competed for general space under the
                             ordinary fee rules, so general got less
```

Two rules govern the boundary, and they are deliberately asymmetric:

- **General transactions can never use the payment lane** — not even when it sits empty. This is where the guarantee comes from: reserved gas that could be resold to general traffic would not be a reservation at all.
- **Payment transactions can use general space** — the payment lane is a floor, never a ceiling. Payment gas beyond it carries no privilege and bids for the remaining space on equal terms with everything else.

The bar is a gas quota, not a layout. [§3.3](#33-reserved-gas-accounting-rule) is this picture written as a single inequality, and says what that means for ordering.

### 3.2 Transaction Classification

A **payment transaction** is one sent to a listed payment asset, or a plain BNB transfer to an account that holds no code — under the conditions common to both, stated below. Every other transaction is a **general transaction**. Nothing is executed to decide this: the class follows from static transaction fields plus at most two state lookups, so it is settled before the transaction runs rather than as a result of running it.

Both rules share three conditions: the transaction is not a system transaction, `to` is non-nil, and the type is `0x00`, `0x01`, or `0x02`. A transaction failing any of them is general whatever its destination.

| Rule | Payment when | Covers |
|---|---|---|
| Listed destination | `to` is on the payment contract list ([§3.6.2](#362-the-payment-contract-list)) | Stablecoins and [BEP-702](./BEP-702.md) native tokens, whatever function is called |
| Bare transfer | `value` is non-zero and `to` has no code | Native BNB payments between accounts |

```
classify(tx, parentState, liveState):    # parentState: end of h-1.  liveState: before this tx applies.
    if isSystemTransaction(tx):                          return GENERAL    # common
    if tx.to == nil:                                     return GENERAL    # common
    if tx.type not in {0x00, 0x01, 0x02}:                return GENERAL    # common

    if tx.to in paymentContractList(parentState):        return PAYMENT    # listed, and stops here

    if tx.value != 0                                                       # bare transfer
       and liveState.codeAt(tx.to) is empty:             return PAYMENT

    return GENERAL
```

Each condition earns its place:

- **Not a system transaction** — the transactions Parlia appends to a block are consensus mechanics, not user traffic. In a valid block they are exactly the ones the engine itself built, so this test reads no state and leaves a client nothing to decide.
- **`to` non-nil** — a contract creation has no destination to test.
- **Non-zero `value`** — a zero-value transfer moves nothing, so reserved gas would be protecting nothing.
- **No code at `to`** — this is what keeps the transfer from running contract code. An account that gains code earlier in the same block, by deployment or by an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) authorisation, holds it by the time the transfer is classified and is general, as is one that already carried a delegation designator.
- **The type restriction** — an allowlist: `0x03` carries blobs, which are not payments, and `0x04` applies its own authorisation list before execution begins, installing code in no state a classifier could read ([§4](#4-rationale)).

The two rules read two different states, and that is deliberate:

- **`parentState`** is the state at the end of the parent block, and the listed-destination rule reads it because list membership is a governance fact that has to be settled before the block does anything — read live, whoever orders the block would decide who is on the list. The list is bounded by the contract ([§3.6.2](#362-the-payment-contract-list)), which is what keeps this lookup finite.
- **`liveState`** is the state after the previous transaction in the block has committed and before any part of this one applies. The bare-transfer rule reads it so that an address which gains code within this same block is recognised as holding it. The admitted types install no code of their own, so that boundary is unambiguous — which is what the type restriction buys.

Because the listed-destination rule can only ever decide *payment* and stops there, no transaction's class is decided by both states: a listed destination is decided by the parent state, and everything else by the live state.

### 3.3 Reserved Gas Accounting Rule

For each block, let:

```
paymentGasUsed   = total gas consumed by payment transactions in the block
generalGasUsed   = the block's gas used less paymentGasUsed
paymentLaneQuota = the gas this block reserves for payment transactions (computed per 3.4)
```

Parlia's system transactions are general ([§3.2](#32-transaction-classification)), so their gas falls on the general side of this rule rather than the payment side.

The block MUST satisfy:

```
generalGasUsed + max(paymentGasUsed, paymentLaneQuota) <= GasLimit
```

Blocks violating this rule MUST be rejected as invalid.

The rule has exactly two regimes:

- **Payment demand meets or exceeds the quota** (`paymentGasUsed >= paymentLaneQuota`): the constraint reduces to the ordinary `paymentGasUsed + generalGasUsed <= GasLimit`. Payment gas beyond the quota competes for the remaining space under the existing priority-fee rules on equal terms with general transactions.
- **Payment demand falls short of the quota** (`paymentGasUsed < paymentLaneQuota`): the shortfall reduces the gas available to general transactions one-for-one, the unused reservation staying idle for that block rather than being released ([§4](#4-rationale)).

The rule constrains only gas totals. It says nothing about where transactions sit inside the block: payment and general transactions may be interleaved arbitrarily, and block producers keep full freedom over transaction selection and ordering within the accounting constraint. No new ordering rule, priority rule, or fee rule is introduced.

### 3.4 The Quota

#### 3.4.1 Definition

`paymentLaneQuota` is a fraction of the block's gas limit:

```
paymentLaneQuota(h) = PAYMENT_LANE_RATIO(h−1) × GasLimit(h) / RATIO_DENOM
```

Throughout, `h` is the block being built or validated and `h−1` is its parent. `PAYMENT_LANE_RATIO` is governable and is read from the parent's post-state, so it carries the index `(h−1)`; `RATIO_DENOM` is a protocol constant and carries none, because it never changes. `GasLimit(h)` is this block's, because this is the block whose space is being reserved.

The quota is therefore a pure function of the ratio in the parent's post-state and this block's gas limit; nothing about the block's own contents enters it. So a producer knows the reservation before it selects a transaction and cannot choose it, and every node derives the same value independently rather than being told it ([§3.5](#35-validation)).

#### 3.4.2 Arithmetic

The quota is consensus-critical, so each step is pinned:

- **The ratio** is an integer against `RATIO_DENOM = 10000`: a stored `N` means `N / 10000`. [§3.6.1](#361-the-ratio) bounds what it may hold, and a block whose ratio falls outside that bound is rejected before this arithmetic runs ([§3.6.4](#364-reading)) — which is what makes the width below sufficient.
- **Converting the ratio to gas** multiplies before dividing and truncates toward zero.
- **The product MUST use widened intermediates**: `PAYMENT_LANE_RATIO × GasLimit` exceeds 64 bits above a `GasLimit` of about `2^53`, and consensus bounds `GasLimit` only by `2^63 − 1`.
- **No floating point.**

#### 3.4.3 Activation

`activation` is the block at which this fork takes effect. The fork installs the system contract of [§3.6.3](#363-the-system-contract) while that block executes, so block `activation`'s post-state is the first to hold the ratio.

The quota is read from the parent's post-state ([§3.4.1](#341-definition)), so the lane applies to a block if and only if its parent is at or after `activation`. Block `activation` is therefore outside the mechanism and not subject to [§3.3](#33-reserved-gas-accounting-rule), and `activation + 1` is the first block the reservation binds in. No pre-fork block is asked for anything.

#### 3.4.4 Worked Example

At `GasLimit = 55,000,000`, BSC mainnet's current value, and the ratio of [§3.6.1](#361-the-ratio):

```
paymentLaneQuota = 500 × 55,000,000 / 10,000 = 2,750,000 gas, 5.0% of the block
```

At 2.75M the reservation holds at most 130 native transfers, or between 45 and 78 stablecoin transfers depending on the token and on whether the recipient already holds a balance — an illustration of capacity, not a guaranteed count.

### 3.5 Validation

A node MUST derive the quota ([§3.4.1](#341-definition)), classify every transaction as it runs ([§3.2](#32-transaction-classification)) to obtain `paymentGasUsed`, and reject the block if [§3.3](#33-reserved-gas-accounting-rule)'s inequality fails. It MUST also reject the block if the ratio it reads falls outside [§3.6.1](#361-the-ratio)'s guard ([§3.6.4](#364-reading)).

The check needs execution, so it happens at execution. On [BEP-675](./BEP-675.md)'s `SendBidBlock` path the validator seals without executing, so the check falls on the local import that follows the broadcast: a violation fails `InsertChain` there and is handled by BEP-675's builder revocation, like any other invalid BidBlock.

### 3.6 Configuration and Governance

Governance can move two things: the ratio ([§3.6.1](#361-the-ratio)) and the payment contract list ([§3.6.2](#362-the-payment-contract-list)). Both live in one system contract ([§3.6.3](#363-the-system-contract)), are read from the parent block's post-state, and change only through the standard BSC on-chain governance process ([§3.6.5](#365-governance-updates)). The accounting rule and the classification behind it are protocol logic and are not governable.

#### 3.6.1 The Ratio

One governable value and two protocol constants:

| Name | Meaning | Kind | Value |
|---|---|---|---|
| `PAYMENT_LANE_RATIO` | The reservation, as a fraction of the gas limit | Governable | `500` (5%) until governance moves it |
| `RATIO_DENOM` | Denominator of the ratio | Protocol constant | `10000` |
| `MAX_PAYMENT_LANE_RATIO` | Upper bound on the ratio | Protocol constant | `1000` (10%) |

A ratio governance has never written reads as `500` ([§3.6.3](#363-the-system-contract) makes "never written" precise), so that is the live reservation until the first governance change — and revising the constant at a later fork revises it on every chain where governance never wrote one. Two clients disagreeing on a single digit derive different quotas from the first lane block onward.

The guard is

```
0 < PAYMENT_LANE_RATIO <= MAX_PAYMENT_LANE_RATIO
```

It is the only bound on the reservation, and what keeps the share from being voted to one that starves general traffic. `MAX_PAYMENT_LANE_RATIO` is a protocol constant rather than a governable one, because a ceiling governance can raise is not a ceiling.

Both sides enforce it: the contract reverts a proposal that fails the guard, so nothing is stored; a node rejects a block whose ratio fails it ([§3.6.4](#364-reading)).

#### 3.6.2 The Payment Contract List

The **payment contract list** is the first rule of [§3.2](#32-transaction-classification). It curates assets, not operations — listing is by address, whatever function a transaction calls — and it does not lift §3.2's common conditions. **The list starts empty: the fork lists nothing, and every entry arrives by governance afterwards.** The contract bounds it at 100,000 entries, because classification reads the whole list against each parent post-state — a bound far above any plausible use, there to keep that read finite rather than to ration listings.

**Stablecoins.** Admission rests on governance judgement alone — off-chain audit history and on-chain reputation — with no mechanical gate behind it. The intended first entries are USDT and USDC: USDT is non-upgradeable, its bytecode fixed since deployment; USDC is an upgradeable proxy, audited on each upgrade under considerable market scrutiny. Governance therefore carries the ongoing monitoring as well as the nomination, and this trust is explicit.

**[BEP-702](./BEP-702.md) native tokens.** These tokens deploy no bytecode, expose a function surface fixed by the protocol standard, and have no upgradeable implementation to drift, so what an ordinary contract needs an audit to establish holds here by construction. What still varies is the issuer's own configuration. A voter must therefore establish that the address lies in BEP-702's reserved native-token space with a token actually created there, and that the token's configuration — admin custody, role assignments, transfer policies, supply cap — is fit for payment use: one whose receiver policy is a narrow allowlist is not a general payment asset.

Neither kind is checked on chain: the protocol reads membership and nothing else, so a listing is exactly as sound as the vote behind it.

**Removal** uses the same vote and takes effect the same way, at any time, for either kind. It strips lane eligibility and nothing else: transactions to a removed address are ordinary general transactions from the next block onward.

#### 3.6.3 The System Contract

The contract is `PaymentLane`, at `0x0000000000000000000000000000000000002007`. The fork installs its code there while block `activation` executes ([§3.4.3](#343-activation)), through the same system-contract upgrade path every earlier BSC fork has used. There is no initializer and no genesis storage: zero is not a settable value for the ratio ([§3.6.1](#361-the-ratio)), so a slot reading zero means governance never wrote one and the getter returns §3.6.1's value. All-zero storage therefore already *is* the configuration of §3.6.1, and installing the code is the whole of activation.

| Slot | Contents |
|---|---|
| 0 | `PAYMENT_LANE_RATIO`, one `uint256` |
| 1 | the payment contract list, as an address array: the entry count in the slot, the entries at consecutive slots from `keccak256(bytes32(1))` |
| 2 | the address-to-position index, which makes membership and removal constant-time |

New storage may only be appended: an insertion or a reorder would reinterpret what these slots already hold.

#### 3.6.4 Reading

A node MUST obtain the ratio and the list through the contract's read-only getters, called against the parent post-state, and MUST NOT decode the slots directly. The getters are the interface because the zero-means-unwritten fallback lives in `getPaymentLaneRatio()`: a node decoding slots would see zero where everyone else sees §3.6.1's value, and derive a quota no one else derives. The layout of [§3.6.3](#363-the-system-contract) is for inspecting storage and checking an upgrade against it. An upgrade MUST preserve these getters and their meaning:

| Getter | Returns |
|---|---|
| `getPaymentLaneRatio()` | the ratio as governance set it, or its §3.6.1 value if governance never did |
| `isPaymentContract(address)` | whether that address is listed |
| `arePaymentContracts(address[])` | the same, one answer per address |
| `paymentContractCount()` | the number of entries |
| `getPaymentContracts(offset, limit)` | one page of entries, together with the total number |

The list is read by paging `getPaymentContracts` until the total is covered. Its order is not stable — a removal moves the last entry into the gap — so an index MUST NOT be carried across blocks, and a page walk MUST be checked against the total each call returns rather than assumed complete.

Two failures of that read must not be confused. A node that cannot reach the parent post-state at all — pruned, not yet synced, unavailable — has learned nothing about the block, and MUST NOT reject it on that account; the fault is local. A getter that answers but answers inconsistently — a total that changes mid-walk, a page shorter than the total requires, the same address twice — is a corruption no honest chain produces, and the block MUST be rejected rather than classified against a list its peers do not share.

A ratio outside the guard of [§3.6.1](#361-the-ratio) is the same kind of corruption, and the node MUST reject the block on reading one. The contract cannot store such a value, so reading one means the code at §3.6.3's address is not the contract this specification defines. Every client MUST apply this check — one that only some clients apply is a split rather than a safeguard — and every client MUST use the same `MAX_PAYMENT_LANE_RATIO`, since a client holding a stale bound rejects blocks its peers accept. The getter returns a `uint256`, so the check MUST be evaluated at that full width and never on a value narrowed first: a truncated value can land inside the guard when the value returned did not. The consequence: a chain that reaches this state produces no further blocks until the code at that address is replaced, and that halt does not clear through governance, because the transaction that would clear it needs a block.

#### 3.6.5 Governance Updates

Changes arrive through a single entry point, `updateParam(string key, bytes value)`, callable only by the governance hub at `0x0000000000000000000000000000000000001007` and so reached by the ordinary BSC governance path: a proposal on the governor at `0x0000000000000000000000000000000000002004`, executed by the timelock at `0x0000000000000000000000000000000000002006` once it passes. Three keys are defined: `paymentLaneRatio` carries a 32-byte value, and `addPaymentContract` and `removePaymentContract` each carry a 20-byte address. Adding an address already listed, removing one that is not, adding one that would carry the list past the bound of [§3.6.2](#362-the-payment-contract-list), and a ratio failing [§3.6.1](#361-the-ratio)'s guard all revert rather than passing silently, so that every accepted call is a real change.

An accepted call lands in the post-state of the block that carries it. Every rule here reads the *parent's* post-state — §3.2 for list membership, §3.4 for the ratio — so a change is invisible to its own block and governs from the next one onward.

## 4. Rationale

**A quota, not a region.** A reserved region would have to sit somewhere in the block, which makes position part of the rule. A gas quota does not: the whole proposal is one accounting inequality checked at validation, with selection, ordering and pricing untouched.

**Classification by destination, not declaration.** Deriving the class from `to` plus state means no new transaction field, no wallet changes, and no user action: the protocol recognises an existing fact rather than accepting a claim.

**The code test reads the live state.** Read against the parent instead, it would stop guaranteeing that nothing runs: one transaction deploying code, and a second behind it in the same block transferring to that address with a large gas limit, would put arbitrary execution inside the quota, at the quota's clearing tip rather than the open market's. An [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) authorisation in an earlier transaction is the same attack without the deployment. Against the live state both are ordinary general transactions. An authorisation in the transfer's *own* transaction applies before execution begins, so no classifier can read the code it installs — which is why [§3.2](#32-transaction-classification) excludes that type.

**Unused quota is idle, not reclaimable.** If the shortfall flowed back to general transactions, excluding payment transactions would cost a producer nothing: the space would simply be resold, and the floor would be a fiction precisely in the congested blocks it exists for. Binding the reservation regardless of realized demand inverts that — reserved gas earns fees only when payment transactions fill it.

## 5. Backward Compatibility

This is a consensus-breaking change and requires a hard fork: it adds a block validity rule and the quota computation behind it. Nothing else changes — not transaction formats, the fee mechanism, ordering, or the block header, in layout or in the meaning of any field. Clients need the classification, the quota derivation and the accounting rule, all fork-gated, and the fork installs one system contract ([§3.6.3](#363-the-system-contract)) through the path earlier BSC forks already use.

Three things downstream tooling should account for:

- **A full block no longer shows `gasUsed / GasLimit` near 1.** The fraction falls short by whatever part of the reservation payment traffic left unused, and it falls shortest when congestion is worst — so explorers, gas-price oracles and alerting that read it as a congestion indicator will read the chain as calmer than it is. Saturation should be read from `gasUsed + max(0, paymentLaneQuota − paymentGasUsed)` against `GasLimit` instead, which is [§3.3](#33-reserved-gas-accounting-rule)'s left-hand side.
- **A general transaction's gas limit can no longer exceed `GasLimit` less the quota, less what the producer holds back for system transactions.** Estimators that cap at the block gas limit model neither term, so a transaction in that band estimates successfully and is never includable. The system-transaction half of that gap predates this proposal; the quota widens it. Payment transactions are unaffected — the reservation is a floor for them, never a ceiling.
- **`paymentGasUsed` is recorded nowhere.** It cannot be read from a header, and recovering it from a body needs the state each transaction ran against, so a client that wants to report it must compute it while executing the block ([§6](#6-security-considerations)).

Otherwise behaviour is as it is today.

## 6. Security Considerations

- **Spam within the lane.** The quota grants no free inclusion: payment transactions compete among themselves for reserved gas under the ordinary priority-fee rules, so a flood pays full fees throughout. Payment gas beyond the quota carries no privilege and displaces general traffic exactly as it would without a lane. The reservation bounds volume, not the size of any one transaction: a single payment transaction may occupy all of it.
- **Bounded waste.** What general traffic gives up is never the whole quota, only the part payment traffic leaves idle, and only in a block its own demand would otherwise have filled. That waste is bounded by the quota in each block and does not accumulate across blocks.
- **Classification agreement.** Two clients that classify a transaction differently do not necessarily disagree on the block carrying it. The split is committed nowhere ([§5](#5-backward-compatibility)), so they disagree only where [§3.3](#33-reserved-gas-accounting-rule)'s inequality binds, which may be much later and on an unrelated block. Classification is the most state-dependent part of this proposal ([§3.2](#32-transaction-classification)), so clients SHOULD expose their computed `paymentGasUsed` per block, so that independent implementations can be compared continuously rather than by waiting for a block validity disagreement to surface one.
- **List governance.** Listing and delisting are ordinary governance votes ([§3.6.2](#362-the-payment-contract-list)), and a governance failure's blast radius is confined to lane eligibility: a wrongly listed contract gains a bounded gas floor, never new execution powers. For a BEP-702 native token a vote can strip eligibility but can never weaken the properties BEP-702 enforces on it.
- **Ratio safety.** What bounds the reservation is the guard of [§3.6.1](#361-the-ratio) and nothing else, and being scale-invariant it holds at every `GasLimit`.
- **Block feasibility at a low gas limit.** Parlia's system transactions are mandatory and count as general gas ([§3.3](#33-reserved-gas-accounting-rule)), so a block with no payment traffic is valid only where `systemGasUsed + paymentLaneQuota <= GasLimit`. That condition is not slack: on mainnet a validator-set update alone has reached 12M gas. Parlia already requires `systemGasUsed <= GasLimit` for the same reason, and already with the same property that a failure does not clear on its own: a breathe block is one whose parent sits in the previous UTC day, so once one is infeasible every later candidate is again a breathe block and fails identically. What this proposal does is narrow that existing margin, by a factor of `RATIO_DENOM / (RATIO_DENOM − PAYMENT_LANE_RATIO)` — 1.05x at the ratio of [§3.6.1](#361-the-ratio), and at most 1.11x anywhere its guard permits, which is what keeps the narrowing bounded rather than votable. Both sides of the condition scale with the chain, a validator set's update cost against that same chain's capacity, so reaching it takes a gas limit driven far below what the validator set was sized for.
