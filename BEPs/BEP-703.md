## 1. Summary

This BEP reserves a small fraction of the gas in every block — the **Payment Lane** — that general transactions cannot use. A payment transaction is a bare BNB transfer, or a transaction to a contract governance has listed as a payment asset ([§3.2](#32-transaction-classification)). The reservation is a per-block gas accounting rule, not a region of the block: payment and non-payment transactions remain freely interleaved, ordered, and priced exactly as today. The lane guarantees gas to payment transactions as a class; it does not promise that any one of them is included.

## 2. Motivation

BSC fixes the base fee at zero ([BEP-226](./BEP226.md)), so inclusion is decided entirely by priority-fee bidding. That works well in the common case, but every class of traffic bids for the same block space: when demand in one class pulses, it raises the price of inclusion for all the others. Payment transactions — stablecoin transfers, exchange deposits and withdrawals, remittances, merchant settlement — are hit hardest. They are time-sensitive, they appear in nearly every block, and they are the least able to defend themselves in a bidding contest, because the sender is an end user or a payment backend rather than an agent that re-prices block by block. So payments are the first traffic crowded out, and moving funds — the chain's most basic function — becomes unreliable precisely when the chain is busiest.

This is not a capacity problem: block space comfortably exceeds payment demand at all times, and BSC's throughput keeps rising. The defect is structural — block space is undivided, so congestion in one class spreads to unrelated classes. A bounded, protocol-level reservation for the payment class cuts that link, and it is cheap: payment transactions are individually small in gas, so the reservation is a small slice of the block, and the fee market and the ordering rules stay untouched.

## 3. Specification

### 3.1 Block Space Model

Every transaction is either a **payment transaction** or a **general transaction** — how that is decided is specified in [§3.2](#32-transaction-classification).

```
Legend   #  general tx gas     =  payment tx gas
         .  space nobody used  :  reserved for payment but unused - general may NOT take it

Schematic, not to scale: the payment lane is 5% of the block at the ratio of §3.6.1.


Today, with no reservation
                   <---------------- GasLimit ---------------->
  quiet           [######====..................................]
  congested       [############################################]
                    general demand alone fills the block, and payment traffic
                    arriving during the pulse is not included


With the payment lane
                   <-------- general space ---------> <-lane-->
  quiet           [######............................|====:::::]
                    gas to spare: the lane costs general nothing

  congested       [##################################|===::::::]
                    payment below the quota: general stops at the lane boundary,
                    and the unused part of the lane stays idle rather than
                    returning to general

  congested       [############################======|=========]
                    payment above the quota: the overflow competed for general
                    space under the ordinary fee rules, so general got less
```

Two rules govern the boundary, and they are deliberately asymmetric:

- **General transactions can never use the payment lane** — not even when it sits empty.
- **Payment transactions can use general space** — the payment lane is a floor, never a ceiling.

[§3.3](#33-reserved-gas-accounting-rule) writes this picture as a single inequality.

### 3.2 Transaction Classification

A **payment transaction** is one sent to a listed payment contract, or a bare BNB transfer to an account that holds no code — under the conditions common to both, stated below. Every other transaction is a **general transaction**. Nothing is executed to decide this: the class follows from static transaction fields plus at most two state lookups, so it is settled before the transaction runs rather than as a result of running it.

Both rules share three conditions: the transaction is not a system transaction, `to` is non-nil, and the type is `0x00`, `0x01`, or `0x02`. A transaction failing any of them is general whatever its destination.

| Rule | Payment when | Covers |
|---|---|---|
| Listed destination | `to` is on the payment contract list ([§3.6.2](#362-the-payment-contract-list)) | Stablecoins and [BEP-702](./BEP-702.md) native tokens, whatever function is called |
| Bare transfer | `value` is non-zero and `to` has no code | Native BNB payments between accounts |

```
classify(tx, parentState, liveState):    # parentState: end of h-1.  liveState: before this tx applies.
    if isSystemTransaction(tx):                          return GENERAL    # common
    if tx.to == nil:                                     return GENERAL    # common
    if tx.type not in {0x00, 0x01, 0x02}:                return GENERAL    # common

    if tx.to in paymentContractList(parentState):        return PAYMENT    # listed, and stops here

    if tx.value != 0                                                       # bare transfer
       and liveState.codeAt(tx.to) is empty:             return PAYMENT

    return GENERAL
```

Each condition earns its place:

- **Not a system transaction** — the transactions Parlia appends to a block are consensus mechanics, not user traffic.
- **`to` non-nil** — a contract creation has no destination to test.
- **Non-zero `value`** — a zero-value transfer moves nothing, so reserved gas would be protecting nothing.
- **No code at `to`** — the account's *own* code, so an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) delegation designator counts as code even though the code it runs lives elsewhere. An account that gains code earlier in the same block, by deployment or by an authorisation, holds it by the time the transfer is classified and is general.
- **The type restriction** — an allowlist: `0x03` carries blobs, which are not payments, and `0x04` installs code before execution begins, so no classifier can read it ([§4](#4-rationale)).

The two rules read two different states, and that is deliberate:

- **`parentState`** is the state at the end of the parent block, and the listed-destination rule reads it because list membership is a governance fact that has to be settled before the block does anything — read live, whoever orders the block would decide who is on the list. Membership is one test against that state, and [§3.6.4](#364-reading) says how it is read.
- **`liveState`** is the state after the previous transaction in the block has committed and before any part of this one applies. The admitted types install no code of their own, so that boundary is unambiguous — which is what the type restriction buys.

Because the listed-destination rule can only ever decide *payment* and stops there, no transaction's class is decided by both states: a listed destination is decided by the parent state, and everything else by the live state.

### 3.3 Reserved Gas Accounting Rule

For each block, let:

```
paymentGasUsed   = the part of the block's gas used that its payment transactions contributed
generalGasUsed   = the block's gas used less paymentGasUsed
paymentLaneQuota = the gas this block reserves for payment transactions (computed per §3.4)
```

Parlia's system transactions are general ([§3.2](#32-transaction-classification)), so their gas falls on the general side of this rule rather than the payment side.

The block MUST satisfy:

```
generalGasUsed + max(paymentGasUsed, paymentLaneQuota) <= GasLimit
```

The rule has exactly two regimes:

- **Payment demand meets or exceeds the quota** (`paymentGasUsed >= paymentLaneQuota`): the constraint reduces to the ordinary `paymentGasUsed + generalGasUsed <= GasLimit`. Payment gas beyond the quota competes for the remaining space under the existing priority-fee rules on equal terms with general transactions.
- **Payment demand falls short of the quota** (`paymentGasUsed < paymentLaneQuota`): the shortfall reduces the gas available to general transactions one-for-one, the unused reservation staying idle for that block rather than being released ([§4](#4-rationale)).

The rule constrains only gas totals. It says nothing about where transactions sit inside the block: payment and general transactions may be interleaved arbitrarily, and block producers keep full freedom over transaction selection and ordering within the accounting constraint. No new ordering rule, priority rule, or fee rule is introduced.

### 3.4 The Quota

#### 3.4.1 Definition

`paymentLaneQuota` is a fraction of the block's gas limit:

```
paymentLaneQuota(h) = PAYMENT_LANE_RATIO(h−1) × GasLimit(h) / RATIO_DENOM
```

Throughout, `h` is the block being built or validated and `h−1` is its parent.

The quota is therefore a pure function of the ratio in the parent's post-state and this block's gas limit; nothing about the block's own contents enters it. So a producer knows the reservation before it selects a transaction and cannot make it depend on the block's contents — the one input it does control, the gas limit, moves only within Parlia's per-block bound, and lowering it cannot increase general space. Every node derives the same value independently rather than being told it ([§3.5](#35-validation)).

#### 3.4.2 Arithmetic

The quota is consensus-critical, so each step is pinned:

- **The ratio** is stored as an integer against `RATIO_DENOM` ([§3.6.1](#361-parameters-and-constants)): a stored `N` means `N / RATIO_DENOM`.
- **Converting the ratio to gas** multiplies before dividing and truncates toward zero.
- **The product MUST use integer intermediates wider than 64 bits**: consensus bounds `GasLimit` only by `2^63 − 1`, so at §3.6.1's ratio bound `PAYMENT_LANE_RATIO × GasLimit` needs up to 73 bits.

#### 3.4.3 Activation

`activation` is the first block for which this fork is active. The fork installs the system contract of [§3.6.3](#363-the-system-contract) while that block executes, so block `activation`'s post-state is the first to hold the ratio.

The quota is read from the parent's post-state ([§3.4.1](#341-definition)), so the lane applies to a block if and only if its parent is at or after `activation`. Block `activation` is therefore outside the mechanism and not subject to [§3.3](#33-reserved-gas-accounting-rule), and `activation + 1` is the first block the reservation binds in.

#### 3.4.4 Worked Example

At `GasLimit = 55,000,000`, BSC mainnet's current value, and the ratio of [§3.6.1](#361-parameters-and-constants):

```
paymentLaneQuota = 500 × 55,000,000 / 10,000 = 2,750,000 gas, 5.0% of the block
```

At 2.75M the reservation holds at most 130 native transfers, or between 45 and 78 stablecoin transfers depending on the token and on whether the recipient already holds a balance.

### 3.5 Validation

A node MUST derive the quota ([§3.4.1](#341-definition)), classify every transaction as it runs ([§3.2](#32-transaction-classification)) to obtain `paymentGasUsed`, and reject the block if [§3.3](#33-reserved-gas-accounting-rule)'s inequality fails. It MUST also reject the block if the ratio it reads falls outside [§3.6.1](#361-parameters-and-constants)'s guard ([§3.6.4](#364-reading)).

The check needs execution, so it happens at execution. On [BEP-675](./BEP-675.md)'s `SendBidBlock` path the validator seals without executing, so the check falls on the local import that follows the broadcast: a violation fails `InsertChain` there and is handled by BEP-675's builder revocation, like any other invalid BidBlock.

### 3.6 Configuration and Governance

Governance can move two things: the ratio ([§3.6.1](#361-parameters-and-constants)) and the payment contract list ([§3.6.2](#362-the-payment-contract-list)). Both live in one system contract ([§3.6.3](#363-the-system-contract)), are read from the parent block's post-state, and change only through the standard BSC on-chain governance process ([§3.6.5](#365-governance-updates)). The accounting rule and the classification behind it are protocol logic and are not governable.

#### 3.6.1 Parameters and Constants

One governable value and three constants:

| Name | Meaning | Kind | Value |
|---|---|---|---|
| `PAYMENT_LANE_RATIO` | The reservation, as a fraction of the gas limit | Governable | `500` (5%) until governance moves it |
| `RATIO_DENOM` | Denominator of the ratio | Protocol constant | `10000` |
| `MAX_PAYMENT_LANE_RATIO` | Upper bound on the ratio | Protocol constant | `1000` (10%) |
| `MAX_PAYMENT_CONTRACTS` | Upper bound on the payment contract list ([§3.6.2](#362-the-payment-contract-list)) | Protocol constant | `100000` entries |

A ratio governance has never written reads as `500`, so that is the live reservation until the first governance change — and revising this default at a later fork revises it on every chain where governance never wrote one.

The guard is

```
0 < PAYMENT_LANE_RATIO <= MAX_PAYMENT_LANE_RATIO
```

It is the only bound on the reservation, and what keeps the share from being voted to one that starves general traffic. `MAX_PAYMENT_LANE_RATIO` is a protocol constant rather than a governable one, because a ceiling governance can raise is not a ceiling.

`MAX_PAYMENT_CONTRACTS` caps the work of materialising the list. The contract enforces it when governance writes ([§3.6.5](#365-governance-updates)) and a node rejects a block whose parent post-state reports more, so the value moves only at a fork, in the contract and every client at once.

#### 3.6.2 The Payment Contract List

The **payment contract list** is the first rule of [§3.2](#32-transaction-classification). It curates assets, not operations — listing is by address, whatever function a transaction calls. **The list starts empty: the fork lists nothing, and every entry arrives by governance afterwards.**

**Stablecoins.** Admission rests on governance judgement alone — audit history and on-chain reputation — with no mechanical gate behind it. The intended first entries are USDT and USDC. Governance carries the ongoing monitoring as well as the nomination.

**[BEP-702](./BEP-702.md) native tokens.** These tokens deploy no bytecode and have no upgradeable implementation to drift, so what an ordinary contract needs an audit to establish holds here by construction. What still varies is the issuer's own configuration, which a voter must judge fit for payment use.

**Removal** is the same vote and takes effect the same way. It strips lane eligibility and nothing else: transactions to a removed address are ordinary general transactions from the next block onward.

#### 3.6.3 The System Contract

The contract is `PaymentLane`, at `0x0000000000000000000000000000000000002007`. The fork installs its code there while block `activation` executes ([§3.4.3](#343-activation)). There is no initializer and no genesis storage: zero is not a settable value for the ratio ([§3.6.1](#361-parameters-and-constants)), so a ratio reading zero means governance never wrote one and the getter returns §3.6.1's value.

#### 3.6.4 Reading

A node MUST obtain the ratio and the list through the contract's read-only getters, called against the parent post-state, and MUST NOT decode the contract's storage directly. The getters are the interface because the zero-means-unwritten fallback lives in `getPaymentLaneRatio()`: a node decoding storage would see zero where everyone else sees §3.6.1's value, and derive a quota no one else derives. These getters MUST be pure functions of this contract's own storage — no environment reads, no calls out. An upgrade MUST preserve them and their meaning:

| Getter | Returns |
|---|---|
| `getPaymentLaneRatio()` | the ratio as governance set it, or its §3.6.1 value if governance never did |
| `isPaymentContract(address)` | whether that address is listed |
| `arePaymentContracts(address[])` | the same, one answer per address |
| `paymentContractCount()` | the number of entries |
| `getPaymentContracts(offset, limit)` | one page of entries, together with the total number |

Membership MUST be what `isPaymentContract` answers against the parent post-state ([§3.2](#32-transaction-classification)); the mechanism a node uses to obtain that answer is not constrained. `paymentContractCount` and `getPaymentContracts` serve inspection and any node that mirrors the list: their order is not stable — a removal moves the last entry into the gap — so an index MUST NOT be carried across blocks.

A node that does not execute a block — snap sync below its pivot — never runs the check of [§3.3](#33-reserved-gas-accounting-rule) on it. One that executes but cannot reach the parent post-state — pruned, unavailable — MUST defer that check rather than treat the block as having passed it: the failure is local, and makes the block neither invalid nor its sender a bad peer.

The ratio getter returns a `uint256`, so the guard MUST be evaluated at that full width and never on a value narrowed first: truncation can land an out-of-guard value inside the guard.

#### 3.6.5 Governance Updates

Changes arrive through a single entry point, `updateParam(string key, bytes value)`, callable only by the governance hub at `0x0000000000000000000000000000000000001007`, so a change follows the ordinary BSC governance path. Three keys are defined: `paymentLaneRatio` carries a 32-byte value, and `addPaymentContract` and `removePaymentContract` each carry a 20-byte address. Adding an address already listed, removing one that is not, adding one that would carry the list past `MAX_PAYMENT_CONTRACTS`, and a ratio failing [§3.6.1](#361-parameters-and-constants)'s guard MUST all revert rather than pass silently, so that every accepted call is a real change.

An accepted call lands in the post-state of the block that carries it. Every rule here reads the *parent's* post-state — §3.2 for list membership, §3.4 for the ratio — so a change is invisible to its own block and governs from the next one onward.

## 4. Rationale

**A quota, not a region.** A reserved region would have to sit somewhere in the block, which makes position part of the rule. A gas quota does not: the whole proposal is one accounting inequality checked at validation, with selection, ordering and pricing untouched.

**Classification by destination, not declaration.** Deriving the class from `to` plus state means no new transaction field, no wallet changes, and no user action: the protocol recognises an existing fact rather than accepting a claim.

**The code test reads the live state.** Read against the parent instead, it would stop guaranteeing that nothing runs: one transaction deploying code, and a second behind it in the same block transferring to that address with a large gas limit, would put arbitrary execution inside the quota, at the quota's clearing tip rather than the open market's. An [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) authorisation in an earlier transaction is the same attack without the deployment. Against the live state both are ordinary general transactions. An authorisation in the transfer's *own* transaction applies before execution begins, so no classifier can read the code it installs — which is why [§3.2](#32-transaction-classification) excludes that type.

**Unused quota is idle, not reclaimable.** If the shortfall flowed back to general transactions, excluding payment transactions would cost a producer nothing: the space would simply be resold, and the floor would be a fiction precisely in the congested blocks it exists for. Binding the reservation regardless of realized demand inverts that — reserved gas earns fees only when payment transactions fill it.

## 5. Backward Compatibility

This is a consensus-breaking change and requires a hard fork: it adds a block validity rule and the quota computation behind it. Nothing else changes — not transaction formats, the fee mechanism, ordering, or the block header, in layout or in the meaning of any field.

Clients need the classification, the quota derivation and the accounting rule, all fork-gated, and the fork installs one system contract ([§3.6.3](#363-the-system-contract)) through the path earlier BSC forks already use. Otherwise behaviour is as it is today.

## 6. Security Considerations

- **Spam within the lane.** Reserved gas is not free gas: a third party flooding the lane bids for it under the ordinary fee rules and pays full fees throughout. Nor does the quota bound any single transaction: one payment transaction may fill the lane, leaving the rest to bid for general space as they would today.
- **Bounded waste.** The reservation withholds only its unfilled portion from general transactions. The rule binds when the block's unused gas is smaller than that shortfall ([§3.3](#33-reserved-gas-accounting-rule)).
- **Block feasibility at a low gas limit.** A gas limit too small for Parlia's mandatory system transactions already leaves no valid block, and such a failure already does not clear on its own. Since that gas counts as general ([§3.3](#33-reserved-gas-accounting-rule)), the lane raises the smallest workable gas limit by about 5.3% at the ratio of [§3.6.1](#361-parameters-and-constants), and by about 11.1% at the maximum ratio. It tightens that existing margin but introduces no new failure mechanism.
