## 1. Summary

This BEP reserves a small, fixed fraction of the gas in every block — the **Payment Lane** — that only payment transactions may consume. The reservation is a per-block gas accounting rule, not a region of the block: payment and non-payment transactions remain freely interleaved, ordered, and priced exactly as today. The lane guarantees gas to payment transactions as a class; it does not promise that any one of them is included. And it only takes effect when the block would otherwise be full: in a block with space left over, nothing changes.

## 2. Motivation

BSC fixes the base fee at zero ([BEP-226](./BEP226.md)), so transaction inclusion is decided entirely by priority-fee bidding. This works well in the common case, but during demand pulses one class of traffic bids up inclusion prices for every other class. Payment transactions — stablecoin transfers, exchange deposits and withdrawals, remittances, merchant settlement — are the traffic hit hardest: they are individually small in gas, time-sensitive, present in the overwhelming majority of blocks, and yet the least able to re-price themselves block by block. When a pulse arrives they are the first traffic crowded out, and the chain's most basic function — moving funds — becomes its least reliable one.

This is not a capacity problem. BSC's throughput is on a sustained upward path, and total block space comfortably exceeds payment demand at all times. The defect is structural: heterogeneous traffic shares one undifferentiated bidding dimension, so local congestion in one class propagates to unrelated classes. A bounded, protocol-level reservation for the payment class severs that propagation path at negligible cost to everything else — and does so without touching the fee market or the ordering rules that the rest of the ecosystem relies on.

## 3. Specification

### 3.1 Block Space Model

This section states the model in pictures; the rules that follow are its formalization. Every transaction is either a **payment transaction** or a **general transaction** — how that is decided is specified in [§3.2](#32-transaction-classification).

```
Legend   #  general tx gas    =  payment tx gas
         :  reserved for payment but unused - general may NOT take it
         .  block space nobody used - either class may take it

Schematic, not to scale: the payment lane is 8% of the block at the ratio of 3.6.1.


Today, with no reservation

                             <---------------- GasLimit ---------------->
  quiet                     [######====..................................]
  congested                 [############################################]
                             general demand alone fills the block; payment
                             traffic arriving during the pulse is not included


With the payment lane

                             <-------- general space ---------> <payment space>
  quiet                     [######............................|====:::::]
                             the block is not full; the lane changes nothing

  congested,                [##################################|===::::::]
  payment < paymentLaneQuota general stops at the lane boundary; the unused
                             part of the lane stays idle, and is not returned
                             to general

  congested,                [############################======|=========]
  payment > paymentLaneQuota payment filled the lane and overflowed past it;
                             the overflow competed for general space under the
                             ordinary fee rules, so general got less
```

Two rules govern the boundary, and they are deliberately asymmetric:

- **General transactions can never use the payment lane** — not even when it sits empty. This is where the guarantee comes from: reserved gas that could be resold to general traffic would not be a reservation at all.
- **Payment transactions can use general space** — the payment lane is a floor, never a ceiling. Payment gas beyond it carries no privilege and bids for the remaining space on equal terms with everything else.

The bar is a gas quota, not a layout. [§3.3](#33-reserved-gas-accounting-rule) is this picture written as a single inequality, and says what that means for ordering.

### 3.2 Transaction Classification

A transaction is a **payment transaction** if and only if it meets two conditions common to both rules below and then satisfies one of them. Every other transaction is a **general transaction**. Nothing is executed to decide this: the class follows from static transaction fields plus bounded state lookups, so it is settled before the transaction runs rather than as a result of running it.

The two rules read two different states, and that is deliberate. The **listed-destination** rule reads the state as of the end of the parent block, because list membership is a governance fact that has to be settled before the block does anything — read live, whoever orders the block would decide who is on the list. The **bare-transfer** rule reads the state as it stands when the transaction is about to run, so that an address which gains code within this same block is recognised as holding it. Because the listed rule can only ever decide *payment* and stops there, no transaction's class is decided by both: a listed destination is decided by the parent state, and everything else by the live state.

The common conditions are that `to` is non-nil and the transaction type is `0x00`, `0x01`, or `0x02`. A transaction failing either is general whatever its destination.

| Rule | Payment when | Covers |
|---|---|---|
| Listed destination | `to` is on the payment contract list ([§3.6.2](#362-the-payment-contract-list)) | Stablecoins and [BEP-702](./BEP-702.md) native tokens, whatever function is called |
| Bare transfer | `value` is non-zero and `to` has no code in the state this transaction is about to run against | Native BNB payments between accounts |

`to` non-nil is what both rules key on: a contract creation has no destination to test. A non-zero `value` is what makes a bare transfer a payment at all: a zero-value transfer moves nothing, so reserved gas would be protecting nothing. No code at `to` is what keeps the transfer from running contract code: an account that gains code earlier in the same block, by deployment or by an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) authorisation, holds it by the time the transfer is classified and is general, as is one that already carried a delegation designator. The type restriction excludes execution that the code test cannot reach ([§4](#4-rationale)).

```
classify(tx, parentState, liveState):    # parentState: end of h-1.  liveState: just before tx runs.
    if tx.to == nil:                                     return GENERAL    # common
    if tx.type not in {0x00, 0x01, 0x02}:                return GENERAL    # common

    if tx.to in paymentContractList(parentState):        return PAYMENT    # listed, and stops here

    if tx.value != 0                                                       # bare transfer
       and liveState.codeAt(tx.to) is empty:             return PAYMENT

    return GENERAL
```

### 3.3 Reserved Gas Accounting Rule

For each block, let:

```
paymentGasUsed   = total gas consumed by payment transactions in the block
generalGasUsed   = the block's gas used less paymentGasUsed
paymentLaneQuota = the gas this block reserves for payment transactions (computed per 3.4)
```

`generalGasUsed` is a residual, not a sum over general transactions, and the difference is not cosmetic. Parlia appends unsigned system transactions to the end of every block — validator reward, slashing, finality reward, and on a breathe block a validator-set update that has reached 12M gas on mainnet — and their gas is in the header's gas used. Defining the residual puts that gas on the general side without asking [§3.2](#32-transaction-classification) to classify a transaction no user submitted; one of those system transactions is a bare value transfer, so the classification route would instead turn on its destination happening to hold code. The obligation to include them also bounds how large a quota a block can carry, in [§6](#6-security-considerations).

The block MUST satisfy:

```
generalGasUsed + max(paymentGasUsed, paymentLaneQuota) <= GasLimit
```

Blocks violating this rule MUST be rejected as invalid.

The rule has exactly two regimes:

- **Payment demand meets or exceeds the quota** (`paymentGasUsed >= paymentLaneQuota`): the constraint reduces to the ordinary `paymentGasUsed + generalGasUsed <= GasLimit`. Payment gas beyond the quota competes for the remaining space under the existing priority-fee rules on equal terms with general transactions.
- **Payment demand falls short of the quota** (`paymentGasUsed < paymentLaneQuota`): the shortfall reduces the gas available to general transactions one-for-one, the unused reservation staying idle for that block rather than being released ([§4](#4-rationale)).

The rule constrains only gas totals. It says nothing about where transactions sit inside the block: payment and general transactions may be interleaved arbitrarily, and block producers keep full freedom over transaction selection and ordering within the accounting constraint. No new ordering rule, priority rule, or fee rule is introduced.

### 3.4 The Quota

#### 3.4.1 Definition

`paymentLaneQuota` is a fixed fraction of the block's gas limit:

```
paymentLaneQuota(h) = PAYMENT_LANE_RATIO(h−1) × GasLimit(h) / RATIO_DENOM
```

Throughout, `h` is the block being built or validated and `h−1` is its parent. `PAYMENT_LANE_RATIO` is governable and is read from the parent's post-state, so it carries the index `(h−1)`; `RATIO_DENOM` is a protocol constant and carries none, because it never changes. `GasLimit(h)` is this block's, because this is the block whose space is being reserved.

The quota is therefore a pure function of the ratio in the parent's post-state and this block's gas limit; nothing about the block's own contents enters it. So a producer knows the reservation before it selects a transaction and cannot choose it, and every node derives the same value independently rather than being told it ([§3.5](#35-validation)).

#### 3.4.2 Arithmetic

The quota is consensus-critical, so each step is pinned:

- **The ratio** is an integer against `RATIO_DENOM = 10000`: a stored `N` means `N / 10000`. [§3.6.1](#361-the-ratio) bounds what it may hold, and a block whose ratio falls outside that bound is rejected before this arithmetic runs ([§3.6.4](#364-reading)) — which is what makes the width below sufficient.
- **Converting the ratio to gas** multiplies before dividing and truncates toward zero.
- **The product MUST use widened intermediates**: `PAYMENT_LANE_RATIO × GasLimit` exceeds 64 bits above a `GasLimit` of about `2^53`, and consensus bounds `GasLimit` only by `2^63 − 1`.
- **No floating point.**

#### 3.4.3 Activation

`activation` is the block at which this fork takes effect. The fork installs the system contract of [§3.6.3](#363-the-system-contract) while that block executes, so block `activation`'s post-state is the first to hold the ratio.

The quota is read from the parent's post-state ([§3.4.1](#341-definition)), so the lane applies to a block if and only if its parent is at or after `activation`. Block `activation` is therefore outside the mechanism and not subject to [§3.3](#33-reserved-gas-accounting-rule), and `activation + 1` is the first block the reservation binds in. No pre-fork block is asked for anything.

#### 3.4.4 Worked Example

At `GasLimit = 55,000,000`, BSC mainnet's current value, and the ratio of [§3.6.1](#361-the-ratio):

```
paymentLaneQuota = 800 × 55,000,000 / 10,000 = 4,400,000 gas, 8.0% of the block
```

At 4.4M the reservation holds at most 209 native transfers, or between 73 and 126 stablecoin transfers depending on the token and on whether the recipient already holds a balance — an illustration of capacity, not a guaranteed count.

### 3.5 Validation

The quota is derived, never asserted ([§3.4.1](#341-definition)): no block carries a claim about it that could be false, so there is nothing about the quota itself to check. What the derivation reads does have to be checked — the ratio, against the guard of [§3.6.1](#361-the-ratio), as [§3.6.4](#364-reading) requires.

What a node MUST check is the rule of [§3.3](#33-reserved-gas-accounting-rule), evaluated over that derived quota and over the payment total from the node's own execution of the block. `paymentGasUsed` follows from classifying each transaction at the point it runs ([§3.2](#32-transaction-classification)); it is not a header field and cannot be obtained any other way. A block failing the rule MUST be rejected as invalid.

The rule cannot be settled before the block has been executed, and nothing here needs it to be. [BEP-675](./BEP-675.md) lets a validator sign a builder's block before executing it; because the block carries no payment-lane value, there is nothing for a builder to misstate and nothing for a validator to verify before it signs. The rule is adjudicated on import, where BEP-675 already places everything a validator cannot settle before sealing.

### 3.6 Configuration and Governance

What is governable is the size of the reservation and the set of contracts whose traffic it covers. The accounting rule and the classification behind it are protocol logic and are not governable. Both live in one system contract ([§3.6.3](#363-the-system-contract)), both are read from the parent block's post-state, and both change only through the standard BSC on-chain governance process ([§3.6.5](#365-governance-updates)).

#### 3.6.1 The Ratio

One value governance can move, and the protocol constants the quota is computed from:

| Name | Meaning | Kind |
|---|---|---|
| `PAYMENT_LANE_RATIO` | The reservation, as a fraction of the gas limit | Governable |
| `RATIO_DENOM` | Denominator of the ratio, fixed at 10000 | Protocol constant |
| `MAX_PAYMENT_LANE_RATIO` | Upper bound on the ratio, fixed at 2000 (20%) | Protocol constant |

```
PAYMENT_LANE_RATIO = 800 (8%)
```

That value is normative, not a suggestion: a ratio governance has never written reads as 800 ([§3.6.3](#363-the-system-contract) makes "never written" precise). So from activation until the first governance change this *is* the reservation, and one never written keeps reading 800 indefinitely — which also means revising it at a later fork revises the reservation on every chain where governance has not written one. Two clients disagreeing on a single digit derive different quotas from the first lane block onward.

The guard is

```
0 < PAYMENT_LANE_RATIO <= MAX_PAYMENT_LANE_RATIO
```

and it is what keeps the reservation from being voted to a share of the block that starves general traffic. It is scale-invariant, so it holds at every `GasLimit`, and it is the only bound on the reservation — what that leaves resting on it is set out in [§6](#6-security-considerations). `MAX_PAYMENT_LANE_RATIO` is a protocol constant rather than a governable one, because a ceiling governance can raise is not a ceiling.

The guard is enforced on both sides. **The contract validates on execution and reverts**, so a proposal outside the guard leaves the stored ratio untouched and what an observer sees is a failed governance transaction. And a node MUST check the ratio it reads against the same guard, rejecting the block when it fails ([§3.6.4](#364-reading)). The getter returns a `uint256`, so that check MUST be evaluated at the full width returned and never on a copy narrowed first: a truncated value can land inside the guard when the value returned did not.

#### 3.6.2 The Payment Contract List

The **payment contract list** is the first rule of [§3.2](#32-transaction-classification). It curates assets, not operations — listing is by address, whatever function a transaction calls — and it does not lift §3.2's common conditions. Two kinds of asset are eligible, on the same vote but different evidence. **The list starts empty: the fork lists nothing, and every entry arrives by governance afterwards.** It is also bounded by the contract, at 100,000 entries, because classification reads the whole list against each parent post-state — a bound far above any plausible use, there to keep that read finite rather than to ration listings.

**Stablecoins.** Admission rests on governance judgement alone — off-chain audit history and on-chain reputation — with no mechanical gate behind it. The intended first entries are USDT and USDC: USDT is non-upgradeable, its bytecode fixed since deployment; USDC is an upgradeable proxy, audited on each upgrade under considerable market scrutiny. Governance therefore carries the ongoing monitoring as well as the nomination, and this trust is explicit.

**[BEP-702](./BEP-702.md) native tokens.** These tokens deploy no bytecode, expose a function surface fixed by the protocol standard, and have no upgradeable implementation to drift, so what an ordinary contract needs an audit to establish holds here by construction. What still varies is the issuer's own configuration, so a voter must additionally establish that the address lies in BEP-702's reserved native-token space with a token actually created there, and that the token's configuration — admin custody, role assignments, transfer policies, supply cap — is fit for payment use; one whose receiver policy is a narrow allowlist is not a general payment asset. None of that is enforced on chain: the protocol reads membership and nothing else, so both kinds of listing are exactly as sound as the vote behind them.

**Removal** uses the same vote and takes effect the same way, at any time, for either kind. It strips lane eligibility and nothing else: transactions to a removed address are ordinary general transactions from the next block onward.

#### 3.6.3 The System Contract

The contract is `PaymentLane`, at `0x0000000000000000000000000000000000002007`. The fork installs its code there while block `activation` executes ([§3.4.3](#343-activation)), through the same system-contract upgrade path every earlier BSC fork has used. There is no initializer and no genesis storage: an unwritten slot reads as zero, zero is not a settable value for the ratio ([§3.6.1](#361-the-ratio)), and a ratio reading zero takes the value §3.6.1 lists for it. All-zero storage therefore already *is* the configuration of §3.6.1, so installing the code is the whole of activation.

| Slot | Contents |
|---|---|
| 0 | `PAYMENT_LANE_RATIO`, one `uint256` |
| 1–2 | the payment contract list, as an enumerable address set: slot 1 the entry count, the entries at consecutive slots from `keccak256(bytes32(1))`, slot 2 the address-to-position index that makes membership and removal constant-time |

New storage may only be appended. An insertion or a reorder moves what a node reads.

#### 3.6.4 Reading

A node MUST obtain the ratio and the list through the contract's read-only getters, called against the parent post-state, and MUST NOT decode the slots directly. The layout above is for inspecting storage and checking an upgrade against it; the getters are the interface, because the zero-means-unwritten fallback lives in `getPaymentLaneRatio()` — a node decoding slots would see zero where everyone else sees §3.6.1's value, and derive a quota no one else derives. An upgrade may move storage, but MUST preserve these getters and their meaning:

| Getter | Returns |
|---|---|
| `getPaymentLaneRatio()` | the ratio as governance set it, or its §3.6.1 value if governance never did |
| `isPaymentContract(address)` | whether that address is listed |
| `arePaymentContracts(address[])` | the same, one answer per address |
| `paymentContractCount()` | the number of entries |
| `getPaymentContracts(offset, limit)` | one page of entries, together with the total number |

The list is read by paging `getPaymentContracts` until the total is covered. Its order is not stable — a removal moves the last entry into the gap — so an index MUST NOT be carried across blocks, and a page walk MUST be checked against the total each call returns rather than assumed complete.

Two failures of that read must not be confused. A node that cannot reach the parent post-state at all — pruned, not yet synced, unavailable — has learned nothing about the block, and MUST NOT reject it on that account; the fault is local. A getter that answers but answers inconsistently — a total that changes mid-walk, a page shorter than the total requires, the same address twice — is a corruption no honest chain produces, and the block MUST be rejected rather than classified against a list its peers do not share.

A ratio outside the guard of [§3.6.1](#361-the-ratio) is the same kind of corruption, and the node MUST reject the block on reading one. The contract cannot store such a value, so reading one means the code at §3.6.3's address is not the contract this specification defines. Every client MUST apply this check — one that only some clients apply is a split rather than a safeguard — and every client MUST use the same `MAX_PAYMENT_LANE_RATIO`, since a client holding a stale bound rejects blocks its peers accept. Note the consequence: a chain that reaches this state produces no further blocks until the code at that address is replaced, and that halt does not clear through governance, because the transaction that would clear it needs a block.

#### 3.6.5 Governance Updates

Changes arrive through a single entry point, `updateParam(string key, bytes value)`, callable only by the governance hub at `0x0000000000000000000000000000000000001007` and so reached by the ordinary BSC governance path: a proposal on the governor at `0x0000000000000000000000000000000000002004`, executed by the timelock at `0x0000000000000000000000000000000000002006` once it passes. Three keys are defined: `paymentLaneRatio` carries a 32-byte value, and `addPaymentContract` and `removePaymentContract` each carry a 20-byte address. Adding an address already listed, removing one that is not, and adding one that would carry the list past the bound of [§3.6.2](#362-the-payment-contract-list) all revert rather than passing silently, so that every accepted call is a real change. A ratio failing [§3.6.1](#361-the-ratio)'s guard reverts the same way.

An accepted call lands in the post-state of the block that carries it. Every rule here reads the *parent's* post-state — §3.2 for list membership, §3.4 for the ratio — so a change is invisible to its own block and governs from the next one onward. The ratio and the listings share that boundary exactly.

## 4. Rationale

**A quota, not a region.** A reserved region would have to sit somewhere in the block, which makes position part of the rule. A gas quota does not: the whole proposal is one accounting inequality checked at validation, with selection, ordering and pricing untouched.

**Classification by destination, not declaration.** Deriving the class from `to` plus state means no new transaction field, no wallet changes, and no user action: the protocol recognises an existing fact rather than accepting a claim.

**The code test reads the live state.** Read against the parent instead, it stops guaranteeing that nothing runs, and the gap is not academic: one transaction deploying code and a second, behind it in the same block, transferring to that address with a large gas limit puts arbitrary execution inside the quota — priced at the quota's clearing tip rather than the open market's, which is cheapest precisely when congestion makes the reservation matter. An [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) authorisation in an earlier transaction of the same block is the same attack without the deployment. Against the live state the destination holds code by the time the transfer is classified, and both are ordinary general transactions. An authorisation carried by the transfer's *own* transaction applies before execution begins, so the code it installs is in no state a classifier can read; that is what §3.2's type restriction excludes.

What that hands the block producer is bounded and points the wrong way for them. They cannot put code at an address they do not control — a `CREATE` address follows from the deployer, and an authorisation needs the authority's own signature — so the only transfers whose class they can move are those to an address that gains code within their block, and the only direction they can move it is *out* of the lane. Code cannot be taken away again to move one in: [EIP-6780](https://eips.ethereum.org/EIPS/eip-6780) deletes only what the same transaction created, and clearing a delegation needs the account's signature. Moving a transfer out lowers `paymentGasUsed`, which raises the idle reservation and tightens [§3.3](#33-reserved-gas-accounting-rule) against the producer's own block: it costs them space and earns them nothing. The price paid for this is predictability rather than safety — for a bare transfer the class now depends on the transaction's position in a block, so it is no longer something a wallet or an explorer can settle from public state before the block exists, and a reorg can change it.

**Unused quota is idle, not reclaimable.** If the shortfall flowed back to general transactions, excluding payment transactions would cost a producer nothing — the space would simply be resold, and the floor would be a fiction precisely in the congested moments it exists for. Binding the reservation regardless of realized demand inverts the economics: reserved gas earns fees only when payment transactions fill it, so including them is the only way to monetize it.

**A fixed ratio, not one that follows congestion.** A reservation that grew under load and shrank in quiet periods would appear to cost less while the chain is idle, and it would not: reserved gas displaces nothing unless the block is otherwise full, so an idle reservation takes space no transaction wanted. A reservation that *does* bind is by definition one whose block filled to the lane boundary, and any signal tracking congestion reads such a block as congested — so a congestion-following quota would stand at its maximum in every block where its size matters, and below it only where its size is free. Where the two forms genuinely differ is the opening blocks of a congestion episode, and there the following one reserves *less*, protecting payment traffic least at exactly the moment [§2](#2-motivation) describes. What it would cost is an accumulator: a quota that is the result of every step taken since activation is recoverable from neither the header chain nor the state, so every block would have to commit it and carry it forward, and two implementations disagreeing on one boundary block would never reconverge. A fixed ratio needs none of that — a pure function of the parent's post-state and this block's gas limit, derived independently by every node, self-correcting on the next block, and leaving the header untouched.

**A ratio, and nothing else.** Expressing the reservation only as a fraction means it never needs re-tuning as block capacity grows, and a gas-limit increase enlarges it in absolute gas while leaving it the same share of the block — which is the quantity the guarantee and its cost are both measured in. A second bound in absolute gas would add nothing governance cannot already do by lowering the ratio, and as capacity grew it would quietly turn the reservation into a shrinking share of the block. A clamp against the gas a block must leave for its system transactions is the same bound in a different disguise: it would carry a constant duplicating one Parlia already owns — a constant that silently goes wrong if Parlia's own ever moves — to close a margin the ratio guard already bounds ([§6](#6-security-considerations)).

## 5. Backward Compatibility

This is a consensus-breaking change and requires a hard fork: it adds a block validity rule and the quota computation behind it. Transaction formats, the fee mechanism and ordering are untouched, so nothing that submits or handles transactions needs to change. The block header does not change either — not its layout, and not the meaning of any field in it.

Node implementations need the accounting rule, the quota derivation and the classification, all fork-gated. The fork also installs one new system contract ([§3.6.3](#363-the-system-contract)), through the path earlier BSC forks already use for that.

Two observable behaviours change, and downstream tooling should account for both:

- **A full block no longer shows `gasUsed / GasLimit` near 1.** That fraction falls short by whatever part of the reservation payment traffic left unused, bounded by the quota. Explorers, gas-price oracles and alerting that read it as a congestion indicator will read low, and will read low precisely when congestion is worst. What saturation should be read from instead is `gasUsed + max(0, paymentLaneQuota − paymentGasUsed)` against `GasLimit` — the left-hand side of [§3.3](#33-reserved-gas-accounting-rule)'s inequality.
- **A single general transaction can no longer declare a gas limit above `GasLimit` less the quota and less whatever a producer holds back for system transactions.** Gas estimators that cap at the block gas limit model neither term, so a transaction in that band estimates successfully and is never includable. The system-transaction half of the gap has existed since Parlia; this proposal widens it by the quota. Payment transactions are unaffected: the reservation is a floor for them, never a ceiling.

The class split is not recorded on chain, and it cannot be recovered from a header; recovering it from a body needs the state each transaction ran against. A client that wants to report `paymentGasUsed` must compute it while executing the block and expose it itself ([§6](#6-security-considerations)).

Otherwise behaviour is as it is today. What general traffic gives up is never the whole quota, only the part payment traffic leaves idle — space payment gas would have taken from it anyway — and only in a block its own demand would otherwise have filled.

## 6. Security Considerations

- **Spam within the lane.** The quota grants no free inclusion: payment transactions compete among themselves for reserved gas under the ordinary priority-fee rules, so a flood pays full fees throughout. Payment gas beyond the quota carries no privilege and displaces general traffic exactly as it would without a lane. The reservation bounds volume, not the size of any one transaction: a single payment transaction may occupy all of it.
- **Bounded waste.** Idle reserved gas is bounded per block by the quota, and it is realized only in a block whose general demand would otherwise have filled it — in an under-filled block the reservation displaces nothing. The bound is per block and does not accumulate.
- **Classification agreement.** Two clients that classify a transaction differently do not necessarily disagree on the block carrying it. The split is committed nowhere ([§5](#5-backward-compatibility)), so they disagree only where [§3.3](#33-reserved-gas-accounting-rule)'s inequality binds, which may be much later and on an unrelated block. Classification is the most state-dependent part of this proposal ([§3.2](#32-transaction-classification)), so clients SHOULD expose their computed `paymentGasUsed` per block, so that independent implementations can be compared continuously rather than by waiting for a block validity disagreement to surface one.
- **List governance.** Listing and delisting are ordinary governance votes ([§3.6.2](#362-the-payment-contract-list)), and a governance failure's blast radius is confined to lane eligibility: a wrongly listed contract gains a bounded gas floor, never new execution powers. For a BEP-702 native token a vote can strip eligibility but can never weaken the properties BEP-702 enforces on it.
- **Ratio safety.** The guard of [§3.6.1](#361-the-ratio) is validated before a change activates, on the contract side and on the node side alike, and it is the whole of what bounds the reservation. It keeps the share from being voted to one that starves general traffic, and being scale-invariant it holds at every `GasLimit`.
- **Block feasibility at a low gas limit.** Parlia's system transactions are mandatory and count as general gas ([§3.3](#33-reserved-gas-accounting-rule)), so a block with no payment traffic is valid only where `systemGasUsed + paymentLaneQuota <= GasLimit`. Parlia already requires `systemGasUsed <= GasLimit` for the same reason, and already with the same property that a failure does not clear on its own: a breathe block is one whose parent sits in the previous UTC day, so once one is infeasible every later candidate is again a breathe block and fails identically. What this proposal does is narrow that existing margin, by a factor of `RATIO_DENOM / (RATIO_DENOM − PAYMENT_LANE_RATIO)` — 1.09x at the ratio of [§3.6.1](#361-the-ratio), and at most 1.25x anywhere its guard permits, which is what keeps the narrowing bounded rather than votable. Both sides of the condition scale with the chain, a validator set's update cost against that same chain's capacity, so reaching it takes a gas limit driven far below what the validator set was sized for.
