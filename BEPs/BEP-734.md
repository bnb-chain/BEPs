## 1. Summary

This BEP adds a validator-local blob inclusion guard to the `SendBidBlock` path introduced by [BEP-675](./BEP-675.md). On a blob-eligible block, a builder-proposed block may enter bid selection only if it contains at least as many blobs as the validator would require from its own executable, sufficiently aged blob pool, capped at six blobs.

The guard makes the validator's local block-building capability the minimum acceptable blob service level for a builder proposal. It does not require a builder to include particular transaction hashes, change transaction ordering, or introduce a new block-validity rule.

## 2. Abstract

For each blob-eligible block, the validator derives a local `requiredBlobCount` from pending blob transactions that are executable against the parent state, can pay the next block's fees, satisfy the validator's minimum execution-gas price, and have remained in the validator's pool for at least five seconds. The requirement is:

```text
requiredBlobCount = min(qualifiedBlobCount, MinRequired)
```

`qualifiedBlobCount` counts blobs, not transactions. `MinRequired` is initially six and MUST NOT exceed six. Therefore, an empty qualified pool creates no obligation; a pool containing one through five qualified blobs requires that exact number; and a pool containing six or more requires six.

A `BidBlock` whose verified blob count is below this requirement is not admitted to the candidate set. Repeated violations revoke the builder's `SendBidBlock` permission for 24 hours. When no admissible builder proposal is available, the validator retains the existing local and legacy proposal paths.

## 3. Motivation

[BEP-675](./BEP-675.md) removed validator-side simulation from the builder-proposed block path. Before its transport was optimized, a bid carrying blob transactions and sidecars took longer to assemble and submit than a bid containing only ordinary transactions. Since winning a block is latency-sensitive, this additional work reduced a builder's probability of winning and gave builders a practical incentive to omit blobs.

The gRPC transport for `SendBidBlock` removed the material submission overhead of blob-bearing bids. That improvement addressed the performance disadvantage, but it did not create an economic reason to include blob transactions. Builders can still maximize their competitiveness while leaving blob capacity unused, and this behavior has persisted even when validators have executable blob transactions in their local pools.

For rollups that use BSC for data availability, delayed inclusion means batches wait longer or compete more aggressively for the few blocks that carry blobs. This has caused L2 batch-posting fees to spike and become less predictable. The problem is no longer primarily transport performance; it is the absence of a minimum inclusion obligation on the dominant builder path.

This BEP closes that gap without turning a validator's local transaction pool into consensus state. A validator simply refuses builder proposals that provide less blob capacity than its own local view justifies. The resulting block remains governed by the existing consensus rules.

## 4. Specification

### 4.1 Scope

The guard applies only when all of the following are true:

1. Blob guard is enabled by validator configuration.
2. The target block is blob-eligible under the active BSC blob schedule, currently the one-in-five schedule defined by [BEP-657](./BEP-657.md).
3. The proposal arrived through the BEP-675 `SendBidBlock` path.

The guard does not apply to non-blob-eligible blocks, the legacy `SendBid` path, or the validator's locally assembled block. It is evaluated before an otherwise valid `BidBlock` enters fee-based candidate selection.

This BEP specifies validator-local admission policy. Failure to satisfy the guard does not make a block invalid under consensus and does not cause peers to reject a block that they receive from the network.

### 4.2 Validator-Local Blob Requirement

For target block `h` with parent `p`, the validator computes:

```text
qualifiedBlobCount = sum(blobCount(tx) for tx in qualified(p, now))
requiredBlobCount  = min(qualifiedBlobCount, MinRequired)
```

The following rules apply:

- Blob count is the number of blobs carried by the transactions, not the number of blob transactions.
- `MinRequired` is initially `6` and MUST satisfy `0 < MinRequired <= 6`.
- `requiredBlobCount` is recomputed for each candidate target block from the validator's current local pool.
- The requirement cannot exceed the protocol's maximum blob count for the target block. If a future protocol change lowers that maximum below `MinRequired`, the effective cap is the protocol maximum.

Examples with the initial configuration:

| Qualified blobs in the validator pool | Required blobs in a BidBlock |
| --- | --- |
| 0 | 0 |
| 1 | 1 |
| 4 | 4 |
| 6 | 6 |
| 9 | 6 |

### 4.3 Qualified Blob Transactions

`qualified(p, now)` contains pending blob transactions that meet all of the following conditions:

1. **Executable nonce sequence** — the transaction is executable against parent `p`; nonce-gapped or otherwise queued transactions do not count.
2. **Sufficient execution fee** — the transaction satisfies the same execution-fee and minimum-tip filters used by the validator's local block builder.
3. **Sufficient blob fee cap** — `BlobGasFeeCap` is at least the blob fee derived for target block `h` from parent `p`.
4. **Complete sidecar** — the transaction has a locally available sidecar that passes the transaction pool's normal structural validation.
5. **Minimum pending age** — the transaction was first seen by this validator no later than `now - MinPendingAge`, where `MinPendingAge` is initially `5 seconds`.

The existing transaction-pool pending filters SHOULD be used for conditions 1 through 4 so the local requirement and local block construction apply the same executability and fee rules.

The transaction pool MUST retain a first-seen timestamp suitable for evaluating condition 5. An implementation MAY reset that timestamp to the reload time after a node restart; doing so delays qualification and MUST NOT cause a transaction to appear older than it is. A monotonic process clock SHOULD be used while the process is running.

The age requirement gives a builder time to receive the same transaction before the validator makes it part of the admission obligation. It does not assert that every builder has received every qualified transaction.

### 4.4 BidBlock Admission

After the ordinary BEP-675 prechecks and cheap blob-sidecar checks succeed, the validator derives `bidBlobCount` from the actual blob transactions and matching sidecars in the decoded `BidBlock`. The header's declared `BlobGasUsed` alone MUST NOT be trusted for this check.

Admission is defined as:

```text
if bidBlobCount < requiredBlobCount:
    reject the BidBlock from candidate selection
else:
    admit the BidBlock to the existing candidate-selection process
```

The check is count-based. A builder MAY satisfy it with any valid blob transactions; the builder is not required to reproduce the validator's local transaction set. All existing limits on blob count, sidecar validity, transaction validity, submission timing, and bid ranking remain unchanged.

The requirement is a floor, not a target. A builder MAY include more than `requiredBlobCount` up to the protocol maximum.

### 4.5 Builder Violations

A **blob inclusion violation** occurs when an authenticated builder submits a `BidBlock` that passes the ordinary structural and parent/header prechecks but fails [§4.4](#44-bidblock-admission). Malformed bids rejected for another reason are handled by the existing BEP-675 rules and are not additionally counted as blob inclusion violations.

To prevent multiple submissions for the same block from multiplying the penalty, at most one violation is counted for a builder for a given target block number.

Each validator maintains a rolling, validator-local violation history per builder:

- Window: `60 seconds`.
- Threshold: `13` distinct blob-eligible target blocks with a violation.
- Consequence: revoke that builder's `SendBidBlock` permission for `24 hours`.

During revocation, the builder may use the legacy `SendBid` path subject to its existing checks. Revocation state SHOULD use the persistence mechanism already used for BEP-675 builder permissions so restarting a validator does not clear the penalty.

### 4.6 Local Fallback

Rejecting a BidBlock under [§4.4](#44-bidblock-admission) removes only that candidate. Other admissible `BidBlock` candidates, legacy `SendBid` candidates, and the validator's local block candidate remain available under the existing block-production flow.

If no admissible builder candidate remains at the selection deadline, the validator MUST retain the ability to seal its locally assembled candidate. This guarantees that the guard cannot force the validator to miss a block merely because builders omitted blobs.

The local fallback includes qualified blob transactions according to the validator's existing transaction-selection rules and protocol blob limit. This BEP does not prescribe their ordering beyond those existing rules.

### 4.7 Configuration and Builder Discovery

The validator configuration adds:

```go
type BlobGuardConfig struct {
    Enabled       bool
    MinPendingAge time.Duration
    MinRequired   uint64
}
```

Initial values are:

```text
Enabled       = false
MinPendingAge = 5 seconds
MinRequired   = 6
```

`MinRequired` MUST be rejected at configuration load time if it is zero or greater than six. Implementations SHOULD reject negative or otherwise invalid `MinPendingAge` values.

`BlobGuardConfig` is exposed through the existing MEV parameter discovery interface so builders can learn whether the guard is active and its static bounds. The validator-local `requiredBlobCount` need not be exposed. A builder that wants admission independent of mempool-view differences can include six valid blobs whenever capacity and available transactions permit.

## 5. Rationale

**Use the local block as the floor.** A fixed non-zero requirement would force builders to include blobs when no demand exists. Deriving the floor from the validator's executable pool creates no obligation when the pool is empty and scales naturally from one blob to the protocol cap.

**Count blobs rather than transactions.** One blob transaction can carry multiple blobs. Counting transactions would allow two bids with materially different data capacity to satisfy the same requirement.

**Cap the requirement at six.** Six is the current per-block blob capacity relevant to this proposal. The cap prevents the local pool from creating an impossible admission condition and means the requirement is exactly the available qualified demand until the block is full.

**Wait five seconds before creating an obligation.** Immediate qualification would penalize a builder for normal propagation delay. Five seconds spans more than one BSC block while remaining short enough to prevent sustained omission from creating a long L2 posting backlog.

**Require a count, not specific hashes.** Validators and builders do not have identical transaction-pool views. Requiring exact hashes would reject honest bids because of propagation order, replacement, or temporary sidecar availability. A count requirement preserves implementation freedom and avoids making one validator's pool contents authoritative.

**Keep the guard outside consensus.** Local transaction pools are neither identical nor consensus-replicated. Using them for block validity would create divergent validity decisions. Restricting the rule to validator-side candidate admission avoids that failure mode.

## 6. Backward Compatibility

No hard fork is required. This BEP changes only validator-side `SendBidBlock` admission and builder permission policy. It does not change block validity, block or transaction encoding, the blob fee market, or peer validation.

The guard is disabled by default. Validators that do not enable it behave exactly as before. Builders remain compatible with validators that enable it, but blob-deficient `BidBlock` submissions may be rejected and repeated violations may temporarily remove their `SendBidBlock` permission.

The legacy `SendBid` path and local block production remain available as defined by BEP-675 and the existing client implementation.

## 7. Security Considerations

**Different mempool views.** Honest builders may have fewer blob transactions than a validator. `MinPendingAge` reduces this risk but cannot eliminate network partitions or asymmetric connectivity. Such a bid is rejected locally; it does not create an invalid block or a consensus fault.

**Count-only protection.** This BEP prevents systematic underuse of blob capacity relative to the validator's local demand, but it does not guarantee inclusion of a particular transaction. A builder could satisfy the count with other valid blobs. Per-transaction censorship resistance would require a stronger commitment mechanism and is outside this BEP.

**Local timestamp manipulation.** First-seen time is local policy input, not consensus input. Implementations should use monotonic elapsed time and must not restore persisted transactions with artificially old timestamps. Incorrect timestamps can make admission too strict or too permissive for one validator but cannot split consensus.

**Self-generated blob traffic.** A party can create blob transactions to raise the local requirement, but doing so must satisfy the same execution-tip and blob-fee conditions and consume blob capacity if included. The six-blob cap bounds the effect. Operators should monitor rejected-bid and local-pool metrics before enabling the guard broadly.

**Penalty evasion.** Builder identities and revocation persistence inherit the BEP-675 trust and registration model. A builder able to cheaply rotate identities could reduce the effect of the 24-hour revocation; builder registration policy must therefore prevent unbounded identity churn.

**Fallback liveness.** The validator must preserve a valid local candidate while evaluating builder proposals. An implementation that discards the local candidate before completing the guard check could turn rejected bids into missed blocks, contrary to [§4.6](#46-local-fallback).
