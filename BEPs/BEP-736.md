## 1. Summary

This BEP introduces two precompiled contracts allowing BSC smart contracts to verify ML-DSA-44 and SLH-DSA-SHA2-128s signatures.

## 2. Abstract

The precompiles implement verification for ML-DSA-44 from [FIPS 204](https://csrc.nist.gov/pubs/fips/204/final) and SLH-DSA-SHA2-128s from [FIPS 205](https://csrc.nist.gov/pubs/fips/205/final). Each accepts a public key, a 32-byte message and a signature, and returns a 32-byte verification result.

## 3. Motivation

A sufficiently capable quantum computer could break the ECDSA signatures used by BSC accounts. Smart contracts can adopt post-quantum signatures, but verifying them in EVM bytecode is expensive. The proposed precompiles reduce this cost, enabling smart contracts to use post-quantum signatures for authorization. For example, ERC-4337 smart accounts can use them to verify UserOperation signatures, providing users with post-quantum-resistant account authorization.

## 4. Specification

### 4.1 Precompiled Contracts

As of `PQ_TIMESTAMP`, two precompiled contracts are added at the addresses below.

| Name | Algorithm | Address |
|---|---|---|
| `MLDSA44VERIFY` | ML-DSA-44 | `0x101` |
| `SLHDSASHA2128SVERIFY` | SLH-DSA-SHA2-128s | `0x102` |

### 4.2 Input

Each input is a byte concatenation, with no function selector, offsets or padding:

```text
publicKey || message || signature
```

| Precompile | Public key | Message | Signature | Total input |
|---|---:|---:|---:|---:|
| `MLDSA44VERIFY` | 1,312 bytes | 32 bytes | 2,420 bytes | 3,764 bytes |
| `SLHDSASHA2128SVERIFY` | 32 bytes | 32 bytes | 7,856 bytes | 7,920 bytes |

Public keys and signatures use the encodings defined by FIPS 204 and FIPS 205, respectively. Both precompiles verify the supplied 32-byte message using the Pure signature scheme with an empty context, as specified in the respective standard.

The input length MUST match exactly. Truncated inputs, trailing bytes and encodings rejected by the standard are invalid.

### 4.3 Output

With sufficient gas, each call returns exactly one 32-byte big-endian unsigned integer:

- `1` if the input is valid and signature verification succeeds.
- `0` if the length, encoding or signature is invalid.

Invalid input or a failed verification does not revert. Insufficient gas follows ordinary EVM out-of-gas behavior. Both operations are read-only and can be called with `STATICCALL`.

### 4.4 Gas Cost

| Precompile | Fixed gas per call |
|---|---:|
| `MLDSA44VERIFY` | 10,000 gas |
| `SLHDSASHA2128SVERIFY` | 60,000 gas |

These costs are based on measured verification time relative to `ECRECOVER` (3,000 gas), with a 25% margin and upward rounding.

### 4.5 Solidity Usage

Pass either precompile address and `abi.encodePacked(publicKey, message, signature)`, with `message` typed as `bytes32`:

```solidity
function verifyPQ(
    address verifier,
    bytes memory input
) internal view returns (bool) {
    (bool ok, bytes memory result) = verifier.staticcall(input);
    return ok && result.length == 32 && abi.decode(result, (uint256)) == 1;
}
```

## 5. Rationale

ML-DSA-44 offers smaller signatures; SLH-DSA-SHA2-128s uses a stateless hash-based construction. A 32-byte message supports application-defined digests with a fixed verification cost.

## 6. Backward Compatibility

Before `PQ_TIMESTAMP`, the target addresses follow ordinary EVM account behavior. After activation, calls to these addresses execute the new verification functions.

## 7. Security Considerations

- **Verification consistency.** Clients must agree on verification results, including malformed inputs. Architecture-specific optimizations must preserve the FIPS verification rules.
- **Account authorization.** Callers must use an authorized public key and accept only a 32-byte result equal to `1`. Signed messages must bind the operation to its chain, account and nonce to prevent replay.
