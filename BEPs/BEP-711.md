## 1. Summary

On BSC, a builder may only submit bids to a validator if its signing key is present in that validator's builder allowlist. Today every validator maintains this allowlist as a static entry in its MEV-Sentry configuration. Any change to the set of builder keys therefore requires contacting each validator individually and following up until every configuration has been updated. This BEP introduces an on-chain **Builder Key Registry** as the single source of truth for the builder key set, and extends MEV-Sentry to synchronize its allowlist from the registry automatically.

## 2. Abstract

The BSC MEV architecture (BEP-322, BEP-675) authenticates builders by recovering the signer of each bid and checking it against an allowlist. The allowlist is currently duplicated in every validator's MEV-Sentry configuration file and only reloaded on restart.

This BEP proposes:

1. A minimal, upgradeable **registry contract** that stores the set of `(address, url, name)` builder key entries, enforces a per-builder key cap, and is managed by a transferable admin.
2. A **synchronization mode** in MEV-Sentry that periodically reads the registry and atomically replaces its in-memory allowlist, keeping the static configuration only as a bootstrap fallback.
3. **Local override lists** so that individual validators retain the ability to accept additional builders or reject specific ones.

```text
Admin updates Registry
        │
        ▼
On-chain builder key set changes
        │
        ▼
Every validator's MEV-Sentry picks up the new set within one polling interval
```

## 3. Motivation

BEP-675 was activated on August 25, 2026, and the large majority of blocks are now constructed through the `SendBidBlock` path. Under this path the validator no longer simulates the bid before sealing; instead, each builder key is bounded by a per-key revocation window, so that a single key can theoretically cause up to 45 bad blocks per day before it is downgraded to the simulation-protected `SendBid` path. The network-wide upper bound on bad blocks therefore scales linearly with the **total number of registered builder keys**.

Before BEP-675, builders benefited from holding multiple keys and submitting multiple times to maximize their chances of hitting the optimal submission time. Under the BidBlock mechanism the submission window is deterministic and this is no longer necessary. The community has consequently proposed capping the number of keys per builder, reducing the total from 33 to 22 and lowering the theoretical daily bad-block bound proportionally.

Executing that reduction, and every subsequent key change, exposes the weakness of the current allowlist mechanism:

- **High coordination cost.** Each change must be communicated to every validator separately and tracked to completion.
- **Slow and uneven activation.** A change only takes effect on a given validator after its operator edits the configuration and restarts MEV-Sentry. Different validators complete this at different times, sometimes days apart, so the reduced bound is not actually reached until the last validator has migrated.
- **Configuration drift.** Because there is no canonical list, validator allowlists diverge over time, and retired keys are rarely cleaned up. A key that is meant to be retired but is still accepted by some validators still counts toward the bad-block bound on those validators.
- **No auditable history.** There is no shared record of when a key was added or removed, or by whom, making it impossible to verify that a cap on keys per builder is actually in force.

A single on-chain registry provides one entry point for all changes, an immutable audit trail, and a deterministic propagation time bounded by the MEV-Sentry polling interval. It turns the key cap from a request that each validator must act on individually into a set that is enforced network-wide as soon as the registry is updated, while leaving each validator free to extend or restrict the set locally.

## 4. Specification

### 4.1 Registry Contract

The registry is a smart contract deployed on BSC (one instance per network). It stores a set of builder key entries:

```solidity
struct Builder {
    address addr;   // builder bid-signing key
    string  url;    // builder public endpoint, used for mev_reportIssue
    string  name;   // builder operator, e.g. "blockrazor"; groups keys for the per-builder cap
}
```

- `addr` is the address recovered from the bid signature and is the allowlist key.
- `url` is required because validators and MEV-Sentry deliver `mev_reportIssue` notifications to the builder's endpoint. Each key carries its own URL because a single builder operator commonly runs one key per region.
- `name` identifies the operator that controls the key. It exists so that the number of keys held by each builder can be counted and capped on-chain, and so that the grouping is readable directly from the registry rather than inferred from URL suffixes. MEV-Sentry does not use `name` for bid authentication.

**Per-builder key cap.** The contract stores a default maximum number of keys per builder and an optional per-builder override. `addBuilder` reverts when adding a new key would exceed the cap for that `name`. The cap applies to additions only; removals are always permitted.

**Interface.** The contract exposes at minimum:

```solidity
// Read
function getBuilders() external view returns (Builder[] memory);
function isBuilder(address addr) external view returns (bool);
function keyCount(string calldata name) external view returns (uint256);
function maxKeys(string calldata name) external view returns (uint256);

// Admin
function addBuilder(address addr, string calldata url, string calldata name) external;
function addBuilders(Builder[] calldata builders) external;
function removeBuilder(address addr) external;
function setDefaultMaxKeys(uint256 max) external;
function setMaxKeys(string calldata name, uint256 max) external;
function transferAdmin(address newAdmin) external;

// Events
event BuilderAdded(address indexed addr, string url, string name);
event BuilderRemoved(address indexed addr, string name);
event MaxKeysUpdated(string name, uint256 max);
event AdminTransferred(address indexed previousAdmin, address indexed newAdmin);
```

- `getBuilders()` returns the complete current set in a single call. The set is expected to remain small (tens of entries), so consumers read it in full rather than tracking incremental changes.
- `addBuilder` and `addBuilders` are idempotent with respect to `addr`: adding an existing address updates its `url` and `name` instead of reverting, and does not count as a new key unless `name` changes. `addBuilders` exists so that the initial set can be loaded in one transaction.
- Events are emitted for every change so that operators and tooling can subscribe to registry updates via `eth_getLogs` without polling.
- The contract has no notion of scheduled activation; a change is visible in the block that includes the transaction.

**Upgradeability and administration.** The contract is deployed behind a proxy so that logic can be upgraded without changing the address consumers are configured with. The admin address is transferable. Recommendations on how the admin and proxy-admin roles should be held are given in [Section 6](#6-security).

### 4.2 MEV-Sentry

MEV-Sentry currently loads `[[Builders]]` entries from its configuration file at startup into an immutable in-memory map, and rejects any bid whose recovered signer is not in the map. This BEP adds a registry synchronization mode.

**Configuration.**

```toml
[Registry]
Enabled         = true
ContractAddress = "0x..."
RPCURL          = "http://<validator-node>:8545"   # should be the validator's own node
PollInterval    = "15s"
BlockTag        = "finalized"
ExtraBuilders   = []   # locally accepted in addition to the registry
BlockedBuilders = []   # locally rejected regardless of the registry

[[Builders]]   # existing static entries, retained only as bootstrap fallback
```

**Allowlist derivation.** The effective allowlist is computed as:

```text
effective = (registry set, or fallback set if the registry has never been read successfully)
            ∪ ExtraBuilders
            − BlockedBuilders
```

**Synchronization loop.**

1. At startup, the current set is initialized from the static `[[Builders]]` configuration.
2. Every `PollInterval`, MEV-Sentry calls `getBuilders()` at the configured `BlockTag`.
3. On a successful, non-empty response, it builds the new effective set, prepares any per-builder client state needed for new entries, and **atomically replaces** the current set. From this point the static `[[Builders]]` entries no longer participate in the allowlist.
4. On a failed read, the current set is retained unchanged.
5. An **empty** response is treated as abnormal (for example, a freshly deployed but not yet populated contract, or a misconfigured address). MEV-Sentry logs a warning and retains the current set.

The replacement is all-or-nothing: the bid-authentication path always observes a single consistent snapshot. A builder entry whose endpoint cannot be dialed at synchronization time is still included in the allowlist; endpoint connectivity only affects issue reporting, not bid acceptance.

**Observability.** MEV-Sentry records the block number at which the current set was read and a fingerprint (hash of the sorted `(addr, url)` list) of the set, and exposes both through metrics and a read-only RPC. This allows operators to confirm that all sentries have converged on the same registry state and to detect any that have fallen behind.

### 4.3 Validator

The validator node maintains its own builder allowlist in `Miner.Mev.Builders`, checked independently of MEV-Sentry on every `SendBid` and `SendBidBlock` request. This BEP does not change the validator node. Instead it defines the invariant that operators must maintain:

> **The validator node's builder set must be a superset of the registry set.**

Because MEV-Sentry authenticates bids before forwarding them, additional entries on the node are harmless: bids from keys not in the registry never reach the node. Missing entries, however, cause the node to reject bids that MEV-Sentry has already accepted. This invariant only holds when all builder traffic to the node passes through MEV-Sentry; a validator that accepts builder connections directly must keep its node set equal to the registry set.

Automatic synchronization of the validator node's allowlist from the registry is out of scope for this revision and may be specified in a follow-up.

### 4.4 Operational Procedures

The invariant in [Section 4.3](#43-validator) dictates the order of operations for each kind of change:

- **Adding a key.** Operators first add the key to their validator node configuration. Only after validators have confirmed the change is the key added to the registry. MEV-Sentry then begins forwarding bids from the new key within one polling interval.
- **Removing a key.** The key is removed from the registry first. MEV-Sentry stops forwarding its bids within one polling interval. Operators may remove the stale entry from the validator node at their convenience.
- **Rotating a key.** Performed as an addition of the new key followed by a removal of the old one.

**Initial deployment.**

1. The initial builder key set is compiled and published to validators.
2. Each validator ensures its node configuration contains every key in the initial set.
3. The registry contract is deployed and populated with the initial set via `addBuilders`.
4. Validators upgrade MEV-Sentry and enable `[Registry]`, retaining their existing `[[Builders]]` entries as fallback.
5. Once synchronization is confirmed, the static `[[Builders]]` entries may be removed; retaining them has no effect on behavior.

## 5. Backward Compatibility

No hard fork is required. The change is confined to MEV-Sentry and a new contract; consensus rules and validator node behavior are unchanged.

MEV-Sentry deployments that do not enable `[Registry]` continue to operate exactly as before, using the static `[[Builders]]` configuration. Builders are unaffected: the bid signing and submission interfaces do not change.

## 6. Security

**Admin key.** The registry admin determines which keys every participating validator accepts. Compromise of this key would allow an attacker to insert arbitrary builder keys network-wide. The admin role should be held by a multisig rather than a single externally owned account, and additions should be subject to a time delay; removals may take effect immediately since they only shrink the accepted set. The proxy-admin role, which controls contract upgrades, should be held separately under the same standard.

**Key cap enforcement.** The per-builder cap is checked against the `name` supplied by the admin, and the contract cannot verify that a key genuinely belongs to the named operator. The cap therefore protects against admin error and makes the number of keys per builder publicly verifiable; it does not by itself constrain a malicious admin, who could register a key under a different name. Constraining the admin remains the role of the multisig and public review of registry changes.

**Data source.** MEV-Sentry reads the registry via `eth_call`. If this call is served by an untrusted RPC provider, a malicious provider could return a fabricated set. MEV-Sentry should read from the validator's own node. Reading at the `finalized` block tag additionally protects against transient reorganizations.

**Fail-safe behavior.** MEV-Sentry never clears its allowlist in response to an error: read failures and empty responses both retain the last known good set. The worst outcome of a registry or RPC outage is that the allowlist becomes stale, not that bid processing stops.

**Validator autonomy.** `ExtraBuilders` and `BlockedBuilders` ensure that adopting the registry does not remove a validator's ability to make independent decisions about which builders it works with. A validator can also disable registry synchronization entirely and revert to static configuration at any time.

**Propagation window.** After a key is removed from the registry, different sentries stop accepting it at different moments within one polling interval. For the low-frequency, non-latency-sensitive changes this registry is intended for, a window of tens of seconds is acceptable.
